## Contexto

> **¿Cuándo usar este playbook?**
> Cuando arrancás un proyecto nuevo, o cuando un proyecto existente se está atrasando en dependencias y querés automatizar el mantenimiento.

Qué vas a lograr:

- ✅ Renovate creando PRs de dependencias automáticamente
- ✅ Solo minor y patch (major bloqueadas, se revisan manualmente)
- ✅ Updates agrupados para revisar una vez por semana/quincena
- ✅ Rutina clara de qué hacer con cada PR

---

## Paso 1: Instalar la GitHub App

1. Ir a [GitHub Apps](https://github.com/apps/renovate) → **Install**
2. Seleccionar los repos a monitorear (o "All repositories")
3. Renovate crea un **onboarding PR** titulado "Configure Renovate"

> ⚠️ **Truco que siempre olvido:** NO mergear el onboarding PR todavía. Primero editar el `renovate.json` en esa misma rama con la config propia (paso 2). Renovate actualiza la descripción del PR automáticamente con la nueva config.

---

## Paso 2: Configurar renovate.json

Editar en la rama del onboarding PR:

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended"],
  "timezone": "America/Bogota",
  "schedule": ["before 7am on Saturday"],
  "prHourlyLimit": 0,
  "labels": ["dependencies"],
  "packageRules": [
    {
      "matchUpdateTypes": ["major"],
      "enabled": false
    },
    {
      "matchUpdateTypes": ["patch"],
      "groupName": "patch updates"
    }
  ]
}
```

Qué hace cada parte:

- `schedule`: PRs solo los sábados temprano (no es hora exacta, es una ventana)
- `prHourlyLimit: 0`: sin límite de PRs/hora (el default es 2, frena el primer batch)
- Major deshabilitadas: no genera ruido; las major se revisan aparte
- Patch agrupados: un solo PR "patch updates" en vez de 5 PRs individuales

Mergear el onboarding PR → Renovate queda activo.

## Lección aprendida (2026-08-08): `schedule` es un filtro, NO un disparador

> ⚠️ **Error real cometido en Ceres:** la primera semana con esta config, Renovate no creó ningún PR. El dashboard mostraba todo en "Awaiting Schedule" y el log decía `Package not scheduled` / `Skipping branch creation as not within schedule` para las 6 ramas.

**Qué pasó:** el `schedule` NO hace que Renovate corra los sábados. La app hosted de Mend corre jobs en su propio ritmo (por pushes a `main` y jobs periódicos de su infraestructura). Cuando un job corre, Renovate pregunta "¿estoy dentro de la ventana?" — si sí, crea los PRs; si no, los salta. El job de esa semana corrió un **viernes 11 AM**, fuera de la ventana `before 7am on Saturday` (~7 horas por semana), así que saltó todo.

**Soluciones (de mejor a peor):**

1. **Ampliar la ventana** → cambiar el schedule a algo que casi garantice que un job caiga dentro:

   ```json
   "schedule": ["every weekend"]
   ```

   o `"on Saturday"` si querés mantener el día. Es el fix definitivo.

2. **Desbloqueo manual desde el dashboard** → marcar el checkbox `🔐 Create all awaiting schedule PRs at once 🔐` en el Dependency Dashboard. Esto "unschedulea" las ramas y en el próximo job se crean ignorando el schedule. Sirve para no esperar una semana.

3. **Checkbox de "manual job"** (el último del dashboard) → fuerza un job inmediato, PERO si corre fuera de la ventana sigue sin crear nada. Solo sirve combinado con el punto 2.

**Regla mental:** ventanas muy angostas (horas específicas) = alta probabilidad de que ningún job caiga dentro. Ventanas de días completos = confiable.

## Paso 3: Rutina de revisión (cada 15 días)

1. Revisar el **Dependency Dashboard** (issue que Renovate crea en el repo) para ver el estado general
2. Para cada PR de Renovate:
   - Minor/patch de libs no críticas → correr CI/tests → merge
   - Minor de libs críticas (vite, react) → skim del changelog en el PR → merge
   - **Vulnerabilidad de seguridad** → prioridad inmediata, no esperar al ciclo
3. Para major pendientes (Renovate no las crea, se ven con `ncu`):
   - `npx npm-check-updates` en el proyecto
   - Leer changelog/migration guide de las major que valgan la pena
   - Rama aparte, una dependencia a la vez, tests completos

## Lección aprendida (2026-08-08): por qué los PRs de npm solo tocan el `pnpm-lock.yaml` (y los de NuGet sí el `.csproj`)

> ⚠️ **Confusión real en Ceres:** los PRs de axios, vite, react, etc. solo modificaban `frontend/pnpm-lock.yaml` y no el `package.json`. No es un bug — es el comportamiento esperado. Las ramas ya lo anuncian con el sufijo `-lockfile` (`renovate/axios-1.x-lockfile`).

**Por qué:** en `package.json` las dependencias tienen rangos (`"axios": "^1.18.1"`). Como la nueva versión (1.19.0) **ya satisface el rango `^1.18.1`**, no hace falta editar el `package.json` — Renovate solo actualiza la versión pineada en el lockfile. Esto lo controla `rangeStrategy` (default `auto` → solo edita `package.json` cuando la nueva versión queda **fuera** del rango).

En cambio, los `.csproj` de NuGet pinean versiones sin rangos (`10.0.9` → `10.0.10`), así que ahí **sí** se edita el archivo de proyecto en cada PR.

**¿Cuándo lockfile-only está bien (apps como Ceres)?**

- ✅ El lockfile es la fuente de verdad de lo que se instala en CI/producción
- ✅ Diffs mínimos, menos ruido en los PRs
- ✅ Un `pnpm install` fresco resolvería la última del rango de todas formas

**¿Cuándo SÍ querés que toque el `package.json`? (librerías publicadas)**

- Querés declarar el mínimo real a tus consumidores (`^1.19.0`)
- Protección contra alguien que borre el lockfile e instale una versión vieja vulnerable

En ese caso, agregar a la config:

```json
{
  "packageRules": [
    {
      "matchManagers": ["npm"],
      "rangeStrategy": "bump"
    }
  ]
}
```

Para Ceres (app, no librería) la decisión fue **dejarlo lockfile-only**.

## Lección aprendida (2026-08-08): `minimumReleaseAge` de pnpm puede rechazar los PRs de Renovate

> ⚠️ **Error real en Ceres:** un PR de Renovate falló con "⚠️ Artifact update problem" y el log mostraba `[ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION]` en `frontend/pnpm-lock.yaml`. Además el PR quedó conflicted contra `main` por una versión distinta de `react-hook-form`.

**Qué pasó:** pnpm 11+ trae una protección de cadena de suministro llamada `minimumReleaseAge` (default **1440 minutos = 1 día**): no instala versiones publicadas hace menos de ese tiempo. En este caso, Renovate actualizó `react-hook-form` a la `7.85.0`, pero esa versión se había publicado **el mismo día** (~17 horas antes) — era literalmente "demasiado fresca" para la política de pnpm. El lockfile ya la contenía, así que TODO `pnpm install` fallaba hasta que la versión cumpliera 24 horas de antigüedad.

⚠️ **No es un ataque ni un bug** — es la protección funcionando tal cual. La versión era legítima, solo muy nueva. El ataque que esto previene: alguien publica una versión comprometida y los bots la instalan en minutos; con la espera de 24h, npm suele detectarla y retirarla antes de que la instales.

**Soluciones (de mejor a peor):**

1. **Alinear Renovate con pnpm (fix definitivo)** → agregar un cooldown en `renovate.json` mayor que el de pnpm, así Renovate no propone versiones que pnpm rechazaría:

   ```json
   {
     "minimumReleaseAge": "2 days"
   }
   ```

   Acepta `"1 day"`, `"2 days"`, `"7 days"`, etc. Con el schedule de fin de semana casi no se nota el retraso, y de paso te protegés de versiones maliciosas que se retiran en las primeras 24-48h.

2. **Esperar y reintentar** → si el error ya ocurrió: la versión "fresca" cumple la edad mínima en ~1 día. Marcar el checkbox de rebase/retry del PR (o renombrar el título a `rebase! ...`) y Renovate regenera el lockfile — eso también resuelve el conflicto de merge, porque el lockfile se reconstruye desde cero (los conflictos en `pnpm-lock.yaml` **nunca se resuelven a mano**).

3. **Excepción puntual en pnpm** (si hay prisa, antes de las 24h) → en `pnpm-workspace.yaml`:

   ```yaml
   minimumReleaseAgeExclude:
     - react-hook-form
   ```

   y luego `pnpm install` para regenerar el lockfile localmente.

4. **Desactivar la política** ❌ → `minimumReleaseAge: 0` funciona, pero apaga una protección de seguridad útil por un problema que se resuelve solo esperando. No recomendado.

**Regla mental:** si Renovate es más rápido que `minimumReleaseAge` de pnpm, sus PRs van a fallar intermitentemente. El cooldown de Renovate debe ser **mayor o igual** que el de pnpm.

**Bonus - excepción para paquetes críticos:** si algún día necesitás que una dependencia se actualice sin esperar (ej. parche de seguridad urgente), se puede exceptuar en `packageRules`:

```json
{
  "matchPackageNames": ["axios"],
  "minimumReleaseAge": "0 days"
}
```

## Paso 4: Dónde leer changelogs

Orden de preferencia:

1. **changelogs.xyz** → `https://changelogs.xyz/<paquete>` (el que mejor funciona)
2. **GitHub Releases** del repo del paquete → fuente de verdad
3. **El propio PR de Renovate** → linkea changelogs y muestra badges de Merge Confidence (age, adoption)

Casos sin changelog (ir directo al repo o al blog oficial):

- TypeScript major → devblogs.microsoft.com/typescript
- `@types/*` → sin changelog, confiar en los tests

## Errores comunes

| Error                                                  | Causa                                                                                               | Solución                                                                                                        |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Renovate no crea PRs                                   | Onboarding PR no mergeado                                                                           | Mergear el PR "Configure Renovate"                                                                              |
| PRs creados en horario raro                            | Timezone no configurada                                                                             | Agregar `"timezone": "America/Bogota"`                                                                          |
| Demasiados PRs individuales                            | Falta grouping                                                                                      | Agregar packageRule con `groupName` para patches                                                                |
| PR major inesperado                                    | Falta la regla de bloqueo                                                                           | packageRule con `matchUpdateTypes: ["major"]`, `enabled: false`                                                 |
| Job corre pero no crea PRs (`not-scheduled` en el log) | El job corrió fuera de la ventana del schedule (es filtro, no trigger)                              | Ampliar schedule a `"every weekend"` o marcar "Create all awaiting schedule PRs" en el dashboard                |
| PR de npm solo modifica el lockfile                    | La nueva versión ya satisface el rango `^` → lockfile-only update                                   | Comportamiento esperado en apps; si es librería, `rangeStrategy: "bump"`                                        |
| PR falla con `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`  | Renovate propuso una versión publicada hace menos de 24h (política `minimumReleaseAge` de pnpm 11+) | Agregar `"minimumReleaseAge": "2 days"` en renovate.json; si ya ocurrió, esperar ~1 día y reintentar con rebase |
