# Contexto

> **¿Cuándo usar este playbook?**
>
> Cuando el backend ya soporta sesiones renovables mediante access tokens y
> refresh tokens, pero el frontend todavía obliga al usuario a iniciar sesión
> nuevamente cada vez que expira el access token.

Este playbook comienza donde termina la implementación backend del refresh.

Ya deberías tener un flujo similar a:

```text
POST /auth/login
      │
      ▼
backend
      │
      ├── access token JWT
      │       ↓
      │     JSON
      │
      └── refresh token opaco
              ↓
         HttpOnly cookie
```

Y también:

```text
POST /auth/refresh
      │
      │ cookie enviada automáticamente
      ▼
backend
      │
      ├── validar refresh token
      ├── revocar token anterior
      ├── crear reemplazo
      ├── crear nuevo access token
      │
      ▼
200 OK
{
  "accessToken": "...",
  "expiresIn": 900
}
```

El problema que falta resolver es:

```text
¿Cómo sabe el frontend cuándo debe llamar /refresh?
```

Una aplicación real no debería obligar a cada componente a hacer esto:

```typescript
try {
  await apiClient.get("/accounts");
} catch (error) {
  if (error.status === 401) {
    await refresh();
    await apiClient.get("/accounts");
  }
}
```

Eso produciría lógica duplicada por toda la aplicación.

Queremos centralizarla:

```text
Component
   │
   ▼
apiClient
   │
   ▼
Backend
   │
   ▼
401 Unauthorized
   │
   ▼
Axios Response Interceptor
   │
   ├── POST /auth/refresh
   ├── actualizar access token
   └── repetir request original
```

Desde el punto de vista del componente:

```typescript
const accounts = await apiClient.get("/accounts");
```

debería continuar funcionando aunque el access token haya expirado, siempre que
el refresh token siga siendo válido.

---

# Objetivo arquitectónico

Queremos mantener responsabilidades separadas:

```text
React Components
       │
       │ consumen API
       ▼
apiClient
       │
       │ HTTP
       ▼
AuthInterceptor
       │
       ├── añade Authorization
       ├── detecta 401
       ├── coordina refresh
       └── reintenta requests
       │
       ▼
AuthContext
       │
       ├── user
       ├── accessToken
       └── estado de sesión
```

Mientras tanto:

```text
Browser
   │
   └── Refresh Token
       HttpOnly Cookie
```

La regla central es:

> **Axios administra transporte y reintentos. React administra el estado de
> autenticación. El navegador administra el refresh token HttpOnly.**

No mezcles estas responsabilidades.

# Modelo mental de la sesión

Antes de implementar código, recordá esta división:

```text
ACCESS TOKEN
────────────
JWT
corta duración
guardado en memoria
JavaScript puede acceder a él
enviado con Authorization: Bearer


REFRESH TOKEN
─────────────
token opaco
larga duración
cookie HttpOnly
JavaScript NO puede leerlo
enviado automáticamente por navegador
```

El frontend conoce:

```text
accessToken
```

pero no conoce:

```text
refreshToken
```

Esto es intencional.

# Flujo final que queremos conseguir

```text
GET /api/accounts
Authorization: Bearer JWT1
        │
        ▼
backend
        │
        ▼
401 Unauthorized
        │
        ▼
response interceptor
        │
        ▼
POST /api/auth/refresh
Cookie: refreshToken=RT1
        │
        ▼
backend
        │
        ├── RT1 → revoked
        ├── crear RT2
        ├── crear JWT2
        │
        ▼
200
{
  accessToken: JWT2
}
Set-Cookie: RT2
        │
        ▼
actualizar AuthContext
        │
        ▼
actualizar accessTokenRef
        │
        ▼
repetir GET /api/accounts
Authorization: Bearer JWT2
        │
        ▼
200 OK
```

Para el componente original todo ocurre transparentemente.

# Paso 1: utilizar una única instancia compartida de Axios

No crees Axios directamente dentro de cada servicio.

Evita:

```typescript
axios.get(...)
axios.post(...)
```

dispersos por toda la aplicación.

Crea una instancia compartida:

```typescript
import axios from "axios";

const apiClient = axios.create({
  baseURL: import.meta.env.VITE_BACKEND_URL || "/api",
  headers: {
    "Content-Type": "application/json",
  },
  withCredentials: true,
});

export default apiClient;
```

La arquitectura queda:

```text
LoginService ───────┐
AccountService ─────┤
CategoryService ────┼──► apiClient
TransactionService ─┤
GymService ─────────┘
```

## ¿Por qué una sola instancia?

Porque los interceptores se registran sobre una instancia concreta.

Si tienes:

```typescript
const authClient = axios.create(...);
const accountClient = axios.create(...);
const transactionClient = axios.create(...);
```

tendrías que mantener los interceptores sincronizados entre todos.

Una única instancia reduce esa complejidad.

# Paso 2: habilitar `withCredentials`

El cliente debe permitir que el navegador envíe cookies cuando corresponda:

```typescript
const apiClient = axios.create({
  baseURL: import.meta.env.VITE_BACKEND_URL || "/api",
  withCredentials: true,
});
```

## ¿Significa que Axios puede leer la cookie HttpOnly?

No.

`withCredentials` no hace esto:

```typescript
const token = document.cookie;
```

Simplemente permite:

```text
Axios
  ↓
Browser
  ↓
adjuntar cookies válidas
  ↓
HTTP Request
```

El refresh token continúa inaccesible desde JavaScript.

---

# Diferencia importante: enviar una cookie no significa leerla

El navegador puede hacer:

```http
POST /api/auth/refresh
Cookie: myapp.refreshToken=RT1
```

sin que React conozca:

```text
RT1
```

Este es precisamente el comportamiento deseado.

# Paso 3: considerar CORS y desarrollo con proxy

Si frontend y backend están realmente en orígenes diferentes:

```text
https://app.example.com
https://api.example.com
```

el backend normalmente necesitará permitir credenciales:

```csharp
policy
    .WithOrigins(allowedOrigins)
    .AllowAnyHeader()
    .AllowAnyMethod()
    .AllowCredentials();
```

No combines:

```csharp
AllowAnyOrigin()
```

con:

```csharp
AllowCredentials()
```

porque las credenciales requieren un origen explícito.

## Proxy de Vite

Durante desarrollo podrías tener:

```text
Browser
   ↓
http://localhost:5173/api
   ↓
Vite Proxy
   ↓
http://localhost:5170
```

Desde la perspectiva del navegador:

```text
frontend → /api
```

parece same-origin.

Por eso un proxy puede ocultar problemas reales de CORS.

Recordá siempre probar también la configuración que usarás en producción.

# Paso 4: reutilizar el mismo contrato de autenticación

Si login y refresh devuelven:

```json
{
  "accessToken": "...",
  "expiresIn": 900
}
```

no necesitas:

```typescript
LoginResponse;
RefreshResponse;
```

con exactamente las mismas propiedades.

Puedes tener:

```typescript
export interface AuthResponse {
  accessToken: string;
  expiresIn: number;
}
```

Y utilizarlo para:

```text
login()
refresh()
```

---

# ¿Por qué importa nombrar bien el contrato?

Porque conceptualmente:

```text
Login
  ↓
AuthResponse


Refresh
  ↓
AuthResponse
```

Ambas operaciones están emitiendo:

```text
estado autenticado renovado
```

No son respuestas estructuralmente diferentes.

# Paso 5: crear la operación `refresh()` en el servicio de autenticación

Suponiendo:

```typescript
import apiClient from "@/shared/services/api/apiClient";
```

puedes implementar:

```typescript
export async function refresh(): Promise<AuthResponse> {
  const response = await apiClient.post<AuthResponse>("/auth/refresh");

  return response.data;
}
```

Observa que no enviamos:

```typescript
{
  refreshToken;
}
```

No existe:

```typescript
refresh(token);
```

La función simplemente ejecuta:

```text
POST /auth/refresh
```

El navegador hace el resto.

---

# ¿Por qué no enviar un body?

Porque el backend espera:

```http
Cookie: myapp.refreshToken=...
```

y no:

```json
{
  "refreshToken": "..."
}
```

Esto mantiene el token fuera del runtime de JavaScript.

# Paso 6: mantener el refresh token fuera de AuthContext

Un contexto de autenticación puede verse así:

```typescript
export interface AuthContextValue {
  user: AuthUser | null;
  accessToken: string | null;
  isAuthenticated: boolean;
  login: (accessToken: string) => void;
  logout: () => void;
}
```

No agregues:

```typescript
refreshToken: string;
```

Ni:

```typescript
setRefreshToken(...)
```

Ni:

```typescript
const refreshToken = localStorage.getItem("refreshToken");
```

La separación correcta es:

```text
React
─────
user
accessToken
isAuthenticated


Browser
───────
refreshToken HttpOnly
```

# Paso 7: mantener el access token en memoria

Un provider sencillo puede utilizar:

```typescript
const [accessToken, setAccessToken] = useState<string | null>(null);

const [user, setUser] = useState<AuthUser | null>(null);
```

Después:

```typescript
const login = (token: string) => {
  const authenticatedUser = getUserFromAccessToken(token);

  setAccessToken(token);
  setUser(authenticatedUser);
};
```

Y:

```typescript
const logout = () => {
  setAccessToken(null);
  setUser(null);
};
```

El access token vive únicamente durante la ejecución de la aplicación.

# Paso 8: estabilizar callbacks del AuthProvider

Si `login` y `logout` van a utilizarse como dependencias de un interceptor
registrado mediante `useEffect`, es útil estabilizar sus referencias.

En lugar de:

```typescript
const login = (token: string) => {
  // ...
};
```

utiliza:

```typescript
const login = useCallback((token: string) => {
  const authenticatedUser = getUserFromAccessToken(token);

  setAccessToken(token);
  setUser(authenticatedUser);
}, []);
```

Y:

```typescript
const logout = useCallback(() => {
  setAccessToken(null);
  setUser(null);
}, []);
```

## ¿Por qué?

En JavaScript:

```typescript
const functionA = () => {};
const functionB = () => {};
```

son referencias diferentes aunque hagan lo mismo.

Sin `useCallback`, cada render del provider puede crear:

```text
login #1
login #2
login #3
```

Si el interceptor depende de:

```typescript
useEffect(() => {
  ...
}, [login, logout]);
```

cada nueva referencia provocaría:

```text
cleanup
↓
eject interceptor
↓
register interceptor again
```

No necesariamente rompe la aplicación, pero es trabajo innecesario y hace más
difícil razonar sobre concurrencia.

Con `useCallback`:

```text
login
logout
```

mantienen referencias estables.

# Paso 9: entender por qué necesitamos un `ref` para el access token

Un interceptor de Axios vive fuera del ciclo normal de renderizado de un
componente.

Podrías pensar en hacer:

```typescript
useEffect(() => {
  apiClient.interceptors.request.use((config) => {
    if (accessToken) {
      config.headers.set("Authorization", `Bearer ${accessToken}`);
    }

    return config;
  });
}, []);
```

Pero existe un problema.

El callback captura el valor de:

```text
accessToken
```

existente cuando se creó el efecto.

Esto se denomina:

```text
stale closure
```

Podría ocurrir:

```text
render inicial
accessToken = null
       ↓
crear interceptor
       ↓
login
       ↓
accessToken = JWT1
       ↓
interceptor todavía recuerda null
```

---

# Paso 10: usar `useRef` como puente entre React y Axios

Crea:

```typescript
const accessTokenRef = useRef<string | null>(accessToken);
```

Después mantenlo sincronizado:

```typescript
useLayoutEffect(() => {
  accessTokenRef.current = accessToken;
}, [accessToken]);
```

Ahora el interceptor consulta:

```typescript
accessTokenRef.current;
```

en el momento exacto de ejecutar la request.

---

# ¿Por qué `useRef`?

Porque cambiar:

```typescript
ref.current;
```

no requiere volver a registrar el interceptor.

Conceptualmente:

```text
React state
   │
   │ sincroniza
   ▼
accessTokenRef
   │
   ▼
Axios interceptor
```

Es un puente entre:

```text
mundo React
```

y:

```text
mundo Axios
```

# Paso 11: implementar el request interceptor

El primer interceptor solamente agrega el JWT.

```typescript
const requestInterceptorId = apiClient.interceptors.request.use((config) => {
  const currentAccessToken = accessTokenRef.current;

  if (currentAccessToken) {
    config.headers.set("Authorization", `Bearer ${currentAccessToken}`);
  } else {
    config.headers.delete("Authorization");
  }

  return config;
});
```

Resultado:

```text
accessToken existe
      ↓
Authorization: Bearer JWT
```

Si no existe:

```text
Authorization eliminado
```

# Paso 12: entender qué debe hacer el response interceptor

El response interceptor reaccionará solamente ante determinados `401`.

Flujo:

```text
response
   │
   ├── 200 → devolver normalmente
   ├── 400 → devolver error
   ├── 403 → devolver error
   ├── 404 → devolver error
   ├── 500 → devolver error
   │
   └── 401
        ↓
      evaluar
        ↓
      refresh
```

No todos los errores deben iniciar una renovación de sesión.

# Paso 13: detectar correctamente errores Axios

El error recibido debería tratarse inicialmente como:

```typescript
unknown;
```

Ejemplo:

```typescript
async (error: unknown) => {
  if (!axios.isAxiosError(error) || error.response?.status !== 401) {
    return Promise.reject(error);
  }

  // refresh logic
};
```

Esto evita asumir que cualquier excepción tiene:

```typescript
error.response.status;
```

# Paso 14: excluir endpoints de autenticación

No todo `401` significa:

```text
access token expirado
```

Por ejemplo:

```text
POST /auth/login
↓
401
```

puede simplemente significar:

```text
email/password incorrectos
```

No queremos:

```text
login
↓
401
↓
refresh
```

Por eso define una lista:

```typescript
const REFRESH_EXCLUDED_ENDPOINTS = [
  "/auth/login",
  "/auth/register",
  "/auth/refresh",
  "/auth/logout",
];
```

Helper:

```typescript
function isRefreshExcluded(url?: string) {
  const path = url?.split("?")[0];

  return REFRESH_EXCLUDED_ENDPOINTS.some((endpoint) =>
    path?.endsWith(endpoint),
  );
}
```

---

# ¿Por qué excluir `/auth/refresh`?

Porque si el refresh token ya no es válido:

```text
POST /auth/refresh
↓
401
```

Si el interceptor intenta refrescar esa misma petición:

```text
refresh
↓
401
↓
refresh
↓
401
↓
refresh
↓
...
```

generarías un loop infinito.

---

# ¿Por qué excluir `/auth/logout`?

Logout puede responder de formas relacionadas con sesión inválida y además
forma parte del sistema de autenticación.

No queremos que cerrar sesión pueda disparar una renovación automática.

# Paso 15: agregar una marca `_retry`

Axios no sabe si una request ya pasó por el flujo de renovación.

Podemos extender su configuración:

```typescript
import type { InternalAxiosRequestConfig } from "axios";

interface RetryableRequestConfig extends InternalAxiosRequestConfig {
  _retry?: boolean;
}
```

Cuando recibamos `401`:

```typescript
if (originalRequest._retry) {
  return Promise.reject(error);
}

originalRequest._retry = true;
```

---

# ¿Qué problema resuelve `_retry`?

Sin la marca:

```text
GET /accounts
↓
401
↓
refresh
↓
retry /accounts
↓
401
↓
refresh
↓
retry
↓
401
...
```

Con `_retry`:

```text
GET /accounts
↓
401
↓
_retry = true
↓
refresh
↓
retry
↓
401
↓
rechazar
```

Una request original puede renovarse:

```text
máximo una vez
```

# Paso 16: entender el problema más importante: concurrencia

Supongamos que una pantalla carga al mismo tiempo:

```text
GET /accounts
GET /categories
GET /transactions
GET /budgets
```

El access token acaba de expirar.

Entonces recibes:

```text
/accounts      → 401
/categories    → 401
/transactions  → 401
/budgets       → 401
```

La implementación ingenua sería:

```text
401 → POST /refresh
401 → POST /refresh
401 → POST /refresh
401 → POST /refresh
```

Esto es especialmente peligroso si el backend utiliza **refresh token
rotation**.

---

# Paso 17: entender por qué la rotación convierte la concurrencia en un problema

Supongamos que la cookie contiene:

```text
RT1
```

La primera petición ejecuta:

```text
POST /refresh
RT1
↓
revocar RT1
↓
crear RT2
```

Ahora RT1 ya no es válido.

Si otras peticiones concurrentes también intentan usar RT1, podrían obtener:

```text
401 Invalid Refresh Token
```

Entonces un access token expirado normal podría terminar destruyendo una
sesión válida simplemente porque varias requests fallaron al mismo tiempo.

---

# Paso 18: no resolver esto solamente con `isRefreshing`

Podrías pensar:

```typescript
let isRefreshing = false;
```

Pero un booleano solamente informa:

```text
hay un refresh ejecutándose
```

No proporciona a las demás requests:

```text
el resultado de ese refresh
```

Necesitamos que todas puedan hacer:

```text
await mismo refresh
```

Por eso es mejor utilizar:

```typescript
Promise<string> | null;
```

# Paso 19: crear una `refreshPromise` compartida

Dentro del efecto que registra los interceptores:

```typescript
let refreshPromise: Promise<string> | null = null;
```

La regla será:

```text
refreshPromise == null
        ↓
crear refresh


refreshPromise != null
        ↓
esperar refresh existente
```

# Paso 20: implementar `getFreshAccessToken`

Ejemplo:

```typescript
const getFreshAccessToken = () => {
  if (!refreshPromise) {
    refreshPromise = refreshRequest()
      .then(({ accessToken }) => {
        accessTokenRef.current = accessToken;

        login(accessToken);

        return accessToken;
      })
      .catch((error: unknown) => {
        accessTokenRef.current = null;

        logout();

        window.location.replace("/login");

        throw error;
      })
      .finally(() => {
        refreshPromise = null;
      });
  }

  return refreshPromise;
};
```

Esta pequeña función contiene una de las partes más importantes de toda la
implementación.

---

# Paso 21: entender cómo funciona la Promise compartida

Primera request:

```text
401
↓
refreshPromise == null
↓
crear Promise
↓
POST /refresh
```

Segunda request:

```text
401
↓
refreshPromise != null
↓
return refreshPromise
```

Tercera:

```text
401
↓
return misma Promise
```

Entonces:

```text
Request A ─┐
Request B ─┼──► refreshPromise ─► POST /refresh
Request C ─┘
```

Solo existe:

```text
1 request de refresh
```

# Paso 22: actualizar `accessTokenRef.current` inmediatamente

Este detalle es fácil de olvidar y puede producir un bug difícil de detectar.

Cuando `/refresh` devuelve:

```text
JWT2
```

podrías pensar que basta:

```typescript
login(accessToken);
```

Pero `login()` actualiza React state.

Eso implica:

```text
setState
↓
React agenda render
↓
render
↓
useLayoutEffect
↓
actualizar ref
```

No necesariamente ocurre antes de reintentar la request.

---

# Posible race condition

Supongamos:

```text
refresh devuelve JWT2
↓
login(JWT2)
↓
retry request inmediatamente
↓
request interceptor
↓
accessTokenRef todavía = JWT1
```

Entonces el request interceptor puede sobrescribir:

```http
Authorization: Bearer JWT2
```

con:

```http
Authorization: Bearer JWT1
```

el token expirado.

Por eso antes de hacer el retry debes ejecutar:

```typescript
accessTokenRef.current = accessToken;
```

y después:

```typescript
login(accessToken);
```

---

# Regla importante

Cuando un valor externo debe utilizarse **inmediatamente** antes del siguiente
render:

```text
actualizar ref
    ↓
actualizar React state
```

Para este caso:

```typescript
accessTokenRef.current = accessToken;
login(accessToken);
```

# Paso 23: implementar el response interceptor

Estructura base:

```typescript
const responseInterceptorId = apiClient.interceptors.response.use(
  (response) => response,

  async (error: unknown) => {
    if (!axios.isAxiosError(error) || error.response?.status !== 401) {
      return Promise.reject(error);
    }

    const originalRequest = error.config as RetryableRequestConfig | undefined;

    if (!originalRequest) {
      return Promise.reject(error);
    }

    if (isRefreshExcluded(originalRequest.url)) {
      return Promise.reject(error);
    }

    if (originalRequest._retry) {
      return Promise.reject(error);
    }

    originalRequest._retry = true;

    try {
      const newAccessToken = await getFreshAccessToken();

      originalRequest.headers.set("Authorization", `Bearer ${newAccessToken}`);

      return apiClient(originalRequest);
    } catch (refreshError: unknown) {
      return Promise.reject(refreshError);
    }
  },
);
```

Ahora analicemos cada parte.

---

# Paso 24: filtrar solamente `401`

```typescript
if (!axios.isAxiosError(error) || error.response?.status !== 401) {
  return Promise.reject(error);
}
```

No deberías utilizar refresh para:

```text
400 Bad Request
403 Forbidden
404 Not Found
409 Conflict
500 Internal Server Error
```

Un refresh solamente intenta resolver:

```text
sesión de acceso expirada
```

---

# Importante: `401` y `403` no significan lo mismo

De forma simplificada:

```text
401
────────────
no hay autenticación válida
token ausente
token expirado
token inválido


403
────────────
sí hay identidad válida
pero no tiene permisos
```

No refresques automáticamente un `403`.

Un token nuevo normalmente no cambiará los permisos del usuario.

Después:

No asumas que siempre existe.

# Paso 32: qué hacer cuando el refresh falla

Puede fallar porque:

```text
cookie no existe;
refresh token expiró;
refresh token fue revocado;
refresh token es desconocido;
sesión terminó;
servidor devuelve 401.
```

En ese momento ya no tenemos una sesión recuperable.

Debemos:

```text
limpiar sesión local
↓
redirigir a login
```

Ejemplo:

```typescript
.catch((error: unknown) => {
  accessTokenRef.current = null;

  logout();

  window.location.replace(
    "/login",
  );

  throw error;
});
```

# ¿Por qué limpiar también el ref?

No basta:

```typescript
logout();
```

porque nuevamente React state puede actualizarse en un render posterior.

Queremos que desde ese instante:

```text
accessTokenRef = null
```

para evitar que otra request inmediata use un token viejo.

---

# Paso 33: evitar múltiples logout concurrentes

Una ventaja adicional de colocar el fallo dentro de:

```text
refreshPromise
```

es que todas las requests están esperando la misma Promise.

Por tanto:

```text
Request A ─┐
Request B ─┼── refreshPromise
Request C ─┘        ↓
                  falla
                    ↓
                  logout
```

No necesitas ejecutar:

```text
logout
logout
logout
```

desde cada request esperando.

La Promise centraliza también el failure path.

# Paso 34: elegir cómo redirigir al login

utilizar una estrategia basada en navegación del router.

```tsx

```

En ese caso:

```text

```

está fuera del contexto del router.

Por tanto no puede simplemente llamar:

```typescript

```

Una solución sencilla para una sesión definitivamente inválida es:

```typescript

```

# ¿Por qué `replace` y no `href`?

`replace` sustituye la entrada actual del historial.

Después de perder la sesión no queremos necesariamente:

```text

↓

```

Además una navegación completa elimina:

```text
estado React en memoria
```

lo cual es razonable cuando la sesión ya no puede recuperarse.

No copies:

```typescript

```

como una regla universal.

Si el interceptor está dentro de React Router y tienes una estrategia de
navegación centralizada, podrías hacerlo de otra manera.

Lo importante es separar:

```text

```

de:

```text
cómo navega tu aplicación
```

# Paso 35: hacer cleanup de los interceptores

`interceptors.use()` devuelve un identificador.

Debes conservarlo:

```typescript
const requestInterceptorId =
  apiClient.interceptors.request.use(...);

const responseInterceptorId =
  apiClient.interceptors.response.use(...);
```

Y en cleanup:

```typescript
return () => {
  apiClient.interceptors.request.eject(requestInterceptorId);

  apiClient.interceptors.response.eject(responseInterceptorId);
};
```

---

# ¿Qué ocurre si no haces `eject()`?

Cada montaje podría agregar otro interceptor:

```text
interceptor #1
interceptor #2
interceptor #3
```

Entonces una request podría pasar varias veces por la misma lógica.

Esto puede ser especialmente confuso durante desarrollo con:

```text
React StrictMode
```

donde los efectos pueden montarse y limpiarse más de una vez para detectar
problemas.

# Paso 36: estructura completa recomendada

Conceptualmente:

```typescript
export function AuthInterceptor() {
  const { accessToken, login, logout } = useAuth();

  const accessTokenRef = useRef<string | null>(accessToken);

  useLayoutEffect(() => {
    accessTokenRef.current = accessToken;
  }, [accessToken]);

  useEffect(() => {
    let refreshPromise: Promise<string> | null = null;

    const getFreshAccessToken = () => {
      // shared refresh
    };

    const requestInterceptorId =
      apiClient.interceptors.request.use(
        // Authorization
      );

    const responseInterceptorId =
      apiClient.interceptors.response.use(
        // response
        // 401 handling
      );

    return () => {
      apiClient.interceptors.request.eject(requestInterceptorId);

      apiClient.interceptors.response.eject(responseInterceptorId);
    };
  }, [login, logout]);

  return null;
}
```

# Paso 38: no colocar la Promise globalmente sin necesidad

Una opción tentadora sería:

```typescript
let refreshPromise: Promise<string> | null = null;
```

fuera de React y fuera del componente.

No siempre es necesario.

Si tienes una única instancia de `AuthInterceptor`, puedes mantenerla dentro

```typescript
useEffect(() => {
  let refreshPromise = null;

  ...
}, []);
```

Eso mantiene el estado de coordinación unido al ciclo de vida del interceptor.

Si en otra arquitectura tienes múltiples instancias o varios consumidores
independientes del interceptor, debes reconsiderar el scope.

# Paso 39: entender qué significa "single-flight refresh"

El patrón que implementamos se conoce conceptualmente como:

```text
single flight
```

Varias operaciones solicitan el mismo trabajo:

```text
refresh session
```

pero solamente la primera lo inicia.

Las demás reutilizan su resultado.

```text
A ─┐
B ─┼──► operation
C ─┘
```

Es distinto de una cola explícita, pero para este caso produce un efecto
similar.

---

# Paso 40: Promise compartida vs cola

Una implementación con cola podría mantener:

```text
waitingRequests[]
```

y después resolver manualmente cada entrada.

Eso funciona, pero añade más estado:

```text
queue
resolve
reject
flush
```

Para un caso simple donde todas las requests necesitan exactamente:

```text
el mismo nuevo access token
```

una Promise compartida es más sencilla:

```typescript
await refreshPromise;
```

Menos código implica menos estados intermedios que razonar.

---

# Paso 41: por qué la concurrencia del frontend también protege al backend

El backend podría tener mecanismos contra reutilización concurrente de refresh
tokens.

Pero el frontend no debería provocar ese escenario innecesariamente.

Si sabes que:

```text
RT1 es single-use
```

no deberías enviar:

```text
RT1
RT1
RT1
RT1
```

simultáneamente.

La Promise compartida convierte:

```text
N requests expiradas
```

en:

```text
1 refresh
```

Esto coopera correctamente con la rotación backend.

---

# Paso 42: qué ocurre después de un refresh correcto

Supongamos:

```text
4 requests → 401
```

Todas esperan:

```text
refreshPromise
```

El backend devuelve:

```text
JWT2
```

Entonces cada request recibe:

```typescript
newAccessToken === JWT2;
```

y ejecuta:

```text
retry original request
```

Resultado:

```text
refresh          → 1 request
business retries → 4 requests
```

Esto es correcto.

No queremos convertir las cuatro peticiones de negocio en una sola.

Solo centralizamos:

```text
la renovación de sesión
```

---

# Paso 43: no refrescar preventivamente si no es necesario

Otra estrategia consiste en leer:

```text
exp
```

del JWT y hacer refresh antes de que expire.

Eso puede ser válido, pero añade:

```text
timers
clock synchronization
app sleep/wake
background tabs
race conditions
```

Para una primera implementación robusta, reaccionar al:

```text
401
```

es mucho más sencillo.

El backend continúa siendo la fuente de verdad sobre si el access token es
válido.

# Paso 44: tener cuidado con un `401` que no representa expiración

Dependiendo de tu API, algunos endpoints podrían responder `401` por razones
diferentes.

El interceptor asume:

```text

→ intentar renovar sesión una vez
```

Por eso es importante:

```text
excluir endpoints de autenticación
```

y establecer contratos HTTP consistentes en backend.

Si necesitas distinguir causas más finamente en el futuro, puedes utilizar un
código de error estructurado.

Para una implementación inicial no es obligatorio.

# Paso 58: errores comunes

| Error                                                  | Problema                                           | Solución                                       |
| ------------------------------------------------------ | -------------------------------------------------- | ---------------------------------------------- |
| Guardar refresh token en React                         | Expone un secreto innecesariamente                 | Mantenerlo en cookie HttpOnly                  |
| Guardarlo en `localStorage`                            | JavaScript y XSS pueden acceder directamente       | Cookie HttpOnly                                |
| No usar `withCredentials`                              | La cookie puede no viajar cuando corresponde       | Configurar cliente                             |
| Crear varios clientes Axios                            | Los interceptores quedan fragmentados              | Compartir una instancia                        |

| Lanzar múltiples refresh simultáneos                   | Rompe fácilmente token rotation                    | Single-flight refresh                          |
| No hacer `eject()`                                     | Acumulación de interceptores                       | Cleanup                                        |
| Crear callbacks nuevos en cada render                  | Re-registro innecesario                            | `useCallback`                                  |

# Paso 64: flujo de sesión irrecuperable

```text
GET /accounts
↓
401
↓
POST /refresh
↓
401
↓
accessTokenRef = null
↓
AuthContext logout
↓
redirect /login
```

La aplicación no debe continuar intentando reparar una sesión que el backend
ya declaró inválida.

---

# Paso 65: relación con logout

Una vez que existe este interceptor, el siguiente bloque natural es logout.

El backend debería implementar:

```text
POST /auth/logout
      │
      ├── leer refresh cookie
      ├── hash
      ├── encontrar token
      ├── revocar
      ├── eliminar cookie
      └── 204
```

Frontend:

```text
logout request
↓
backend revocation
↓
AuthContext logout
↓
redirect
```

Recuerda que:

```text
/auth/logout
```

debe estar excluido del refresh automático.

No queremos:

```text
logout
↓
401
↓
refresh
```

---

# Paso 66: relación con Route Guards

El interceptor resuelve:

```text
sesión expira mientras la app está funcionando
```

Pero existe otro problema distinto:

```text
usuario recarga la página
```

Como el access token vive solo en memoria:

```text
F5
↓
React state desaparece
↓
accessToken = null
```

Aunque todavía exista una cookie de refresh válida.

Por eso, posteriormente puedes implementar un flujo de:

```text
application startup
↓
POST /refresh
↓
¿200?
 ├── sí → restaurar AuthContext
 └── no → usuario anónimo
```

Eso pertenece normalmente a:

```text
session bootstrap
route guards
auth initialization
```

No debe confundirse con el interceptor de `401`.

---

# Diferencia entre interceptor y restauración inicial

```text
INTERCEPTOR
───────────
app ya está corriendo
había access token
token expira
request obtiene 401
renovar automáticamente


SESSION RESTORE
───────────────
app acaba de arrancar
no existe access token en memoria
puede existir refresh cookie
intentar restaurar sesión
```

Son problemas relacionados pero diferentes.

# Checklist final

## Cliente HTTP

- [ ] Existe una única instancia compartida de Axios
- [ ] Tiene `baseURL` centralizado
- [ ] Tiene `withCredentials: true`
- [ ] Login, refresh y demás servicios utilizan esa instancia

## Estado de autenticación

- [ ] El access token vive en memoria
- [ ] El usuario vive en AuthContext o estado equivalente
- [ ] El refresh token NO vive en React
- [ ] El refresh token NO vive en `localStorage`
- [ ] El refresh token NO vive en `sessionStorage`
- [ ] `login` actualiza access token y usuario
- [ ] `logout` limpia ambos
- [ ] Los callbacks usados por el interceptor son estables cuando corresponde

## Request interceptor

- [ ] Existe `accessTokenRef`
- [ ] El ref se sincroniza con React state
- [ ] El interceptor lee `accessTokenRef.current`
- [ ] Agrega `Authorization: Bearer`
- [ ] Elimina Authorization si no existe sesión

## Response interceptor

- [ ] Solo maneja errores Axios válidos
- [ ] Solo intenta refresh para `401`
- [ ] No refresca `403`
- [ ] Recupera la request original
- [ ] Excluye `/auth/login`
- [ ] Excluye `/auth/register`
- [ ] Excluye `/auth/refresh`
- [ ] Excluye `/auth/logout`

## Prevención de loops

- [ ] Existe una propiedad `_retry`
- [ ] Se marca antes de iniciar refresh
- [ ] Una request se reintenta como máximo una vez
- [ ] `/auth/refresh` no entra al mismo flujo automático

## Concurrencia

- [ ] Existe una `refreshPromise`
- [ ] Solo la primera request inicia `/refresh`
- [ ] Requests concurrentes esperan la misma Promise
- [ ] Solo existe un refresh para múltiples `401`
- [ ] Todos reciben el nuevo access token
- [ ] Token rotation backend no recibe múltiples usos innecesarios del mismo token

## Actualización del token

- [ ] `accessTokenRef.current` se actualiza inmediatamente
- [ ] React state se actualiza con el token nuevo
- [ ] La request original recibe `Authorization` nuevo
- [ ] El retry utiliza `apiClient`
- [ ] El request interceptor ve el token nuevo

## Refresh fallido

- [ ] `accessTokenRef.current = null`
- [ ] Se limpia AuthContext
- [ ] Se redirige al login
- [ ] No existen múltiples logout concurrentes
- [ ] No existe loop de refresh

## Lifecycle

- [ ] Se guarda el ID del request interceptor
- [ ] Se guarda el ID del response interceptor
- [ ] Ambos hacen `eject()` en cleanup
- [ ] React StrictMode no acumula interceptores

## Pruebas

- [ ] Login correcto funciona
- [ ] Login incorrecto no intenta refresh
- [ ] Cookie HttpOnly existe
- [ ] `/refresh` manual funciona
- [ ] Un access token expirado provoca refresh automático
- [ ] La request original se reintenta
- [ ] El retry utiliza el JWT nuevo
- [ ] Varias requests concurrentes producen un solo refresh
- [ ] Refresh inválido limpia la sesión
- [ ] Refresh inválido redirige al login
- [ ] No existen loops infinitos
- [ ] Una request solo se reintenta una vez
- [ ] `pnpm build` funciona
- [ ] `pnpm lint` funciona

# Qué recordar dentro de seis meses

Si olvidaste casi toda la implementación, recuerda estas cinco ideas.

## 1. El refresh token no pertenece a React

```text
Refresh Token
↓
HttpOnly Cookie
↓
Browser
```

No:

```text
localStorage
React Context
sessionStorage
```

---

## 2. El interceptor reacciona al 401

```text
request
↓
401
↓
refresh
↓
nuevo JWT
↓
retry
```

---

## 3. Cada request solo tiene un intento

```text
_retry
```

evita:

```text
401 → refresh → retry → 401 → refresh...
```

---

## 4. Muchas requests comparten un solo refresh

```text
401 ─┐
401 ─┼── refreshPromise ─► /refresh
401 ─┘
```

Esto es especialmente importante cuando el backend utiliza refresh token
rotation.

---

## 5. Actualiza el ref antes del retry

```typescript
accessTokenRef.current = newAccessToken;

login(newAccessToken);

return apiClient(originalRequest);
```

No confíes solamente en que React state se actualizará antes de que Axios
vuelva a ejecutar la request.

# Secuencia completa de una sesión

Login:

```text
credentials
↓
JWT1 + RT1
```

Uso normal:

```text
JWT1
↓
requests
↓
200
```

```text
JWT1 expired
↓
request
↓
401
```

```text
RT1
↓
```

```text

↓
JWT2
↓
200
```

```text
JWT2 expired

RT2

JWT3 + RT3
```

```text
logout
↓
revocar RT3
↓
borrar cookie
↓
limpiar React
```
