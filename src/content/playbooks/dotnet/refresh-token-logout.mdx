# Contexto

> **¿Cuándo usar este playbook?**
>
> Cuando ya tenés login, refresh tokens, rotación y renovación automática del
> access token, pero todavía necesitás cerrar correctamente una sesión tanto en
> el servidor como en el cliente.

Este playbook cierra el ciclo iniciado por los playbooks anteriores:

```text
1. Persistencia
   ↓
RefreshToken + TokenHash + RevokedAt

2. Emisión y rotación
   ↓
Login + cookie HttpOnly + POST /refresh

3. Refresh automático
   ↓
Axios interceptor + retry + single-flight refresh

4. Logout
   ↓
revocar sesión renovable
+
eliminar cookie
+
limpiar estado local
```

Hasta este punto una aplicación puede mantener una sesión durante mucho tiempo:

```text
Login
  ↓
JWT1 + RT1
  ↓
JWT1 expira
  ↓
Refresh
  ↓
JWT2 + RT2
  ↓
JWT2 expira
  ↓
Refresh
  ↓
JWT3 + RT3
```

Lo que falta resolver es:

```text
¿Qué ocurre cuando el usuario decide terminar esa sesión?
```

Una respuesta incompleta sería:

```typescript
setAccessToken(null);
setUser(null);
```

Eso solamente limpia React.

Si el refresh token continúa activo en servidor:

```text
RT3
↓
sigue siendo válido
↓
POST /refresh todavía podría renovar la sesión
```

Por eso un logout completo necesita dos operaciones:

```text
SERVIDOR
────────
invalidar la sesión renovable


CLIENTE
───────
eliminar el estado autenticado local
```

La regla principal de este playbook es:

> **Logout no es borrar un JWT. Logout es impedir que la sesión pueda seguir
> renovándose y limpiar el estado autenticado del cliente.**

# Antes de empezar: qué significa realmente "cerrar sesión"

En este modelo existen dos credenciales.

## Access token

```text
JWT
corta duración
stateless
guardado en memoria
enviado como Bearer token
```

Por ejemplo:

```http
Authorization: Bearer eyJhbGciOi...
```

Normalmente el servidor no guarda ese JWT.

Por tanto, cuando fue emitido:

```text
JWT válido
↓
seguirá siendo criptográficamente válido
↓
hasta expirar
```

aunque el usuario haga logout.

---

## Refresh token

```text
opaco
larga duración
stateful
cookie HttpOnly
hash persistido en DB
revocable
```

Este token representa la capacidad de continuar la sesión.

Por eso:

```text
Access Token
────────────
permite usar la sesión ahora


Refresh Token
─────────────
permite extender la sesión después
```

Logout debe destruir principalmente la segunda capacidad.

---

# ¿Por qué no borrar el access token desde el backend?

Porque, en una arquitectura JWT stateless, el backend no tiene normalmente algo como:

```text
ActiveAccessTokens
```

contra lo cual consultar cada request.

Si agregáramos:

```text
JWT jti blacklist
```

cada request autenticada podría requerir comprobar:

```text
¿este JWT fue revocado?
```

Eso cambia el modelo operativo.

Para una implementación sencilla y coherente:

```text
access token
→ corto
→ stateless
→ expira naturalmente


refresh token
→ largo
→ stateful
→ revocable
```

Por eso logout hace:

```text
refresh token
↓
RevokedAt = now
```

y el frontend hace:

```text
accessToken = null
```

El JWT antiguo podría seguir siendo técnicamente válido hasta su expiración, pero
el cliente deja de utilizarlo y la sesión ya no puede renovarse.

# Paso 1: definir la semántica del endpoint

El endpoint recomendado es:

```http
POST /api/auth/logout
```

Y su contrato es deliberadamente simple:

```http
204 No Content
```

No necesitas devolver:

```json
{
  "success": true
}
```

ni:

```json
{
  "message": "Logged out"
}
```

porque el resultado útil es el cambio de estado:

```text
antes
─────
sesión renovable posiblemente activa


después
───────
esa sesión ya no debe poder renovarse
```

---

# Paso 2: hacer logout idempotente

Una de las decisiones más importantes es que logout sea **idempotente**.

Una operación idempotente puede ejecutarse varias veces y mantener el mismo
estado final.

Queremos:

```text
logout #1
↓
204

logout #2
↓
204

logout #3
↓
204
```

Incluso si después del primer logout:

```text
la cookie ya no existe
```

o el refresh token:

```text
ya está revocado
```

---

# ¿Qué casos deben producir 204?

Como mínimo:

```text
cookie ausente
→ 204


token desconocido
→ 204


token expirado
→ 204


token ya revocado
→ 204


token activo
→ revocar
→ 204
```

La idea es:

> **El cliente pide que la sesión termine. Si ya estaba terminada, el objetivo
> ya está cumplido.**

---

# ¿Por qué no devolver 401 para un token desconocido?

Podrías hacer:

```text
token válido
→ 204

token desconocido
→ 401
```

pero eso obliga al cliente a conocer estados internos que no necesita.

También crea una diferencia observable:

```text
"este token existía"
vs
"este token nunca existió"
```

Logout no necesita revelar esa información.

Una semántica uniforme es más fácil de consumir:

```text
POST /logout
↓
204
```

---

# Paso 3: no exigir un access token válido para logout

Este punto suele olvidarse.

Supongamos:

```text
15:00
login

15:15
JWT expira

15:16
usuario pulsa "Cerrar sesión"
```

La cookie del refresh token puede seguir siendo válida.

Si `/logout` exige:

```http
Authorization: Bearer <JWT vigente>
```

el usuario podría no poder cerrar correctamente la sesión.

Por eso el endpoint debería poder operar usando:

```text
refresh cookie
```

como identificador de la sesión renovable.

En Minimal APIs puedes dejar esto explícito:

```csharp
auth.MapPost("/logout", LogoutAsync)
    .AllowAnonymous();
```

Aunque el grupo actual no requiera autenticación, declararlo explícitamente
documenta una regla importante y protege el comportamiento ante refactors
futuros.


# ¿Por qué aceptar `null`?

Porque:

```text
no existe cookie
```

no es un error para logout.

El servicio debe poder recibir:

```csharp
await authService.LogoutAsync(null);
```

y simplemente concluir:

```text
no existe una sesión que revocar
```

Eso permite que la idempotencia sea parte de la lógica de Application y no un
detalle accidental del endpoint.

# Paso 5: decidir si necesitas un `LogoutResult`

Normalmente no.

Login puede necesitar estados como:

```text
Success
InvalidCredentials
```

Refresh puede necesitar:

```text
Success
InvalidToken
```

Pero logout deliberadamente colapsa muchos estados en el mismo resultado:

```text
sin cookie
desconocido
expirado
revocado
activo revocado correctamente

↓
204
```

Por tanto esto suele ser suficiente:

```csharp
Task LogoutAsync(...)
```

Evita introducir sin necesidad:

```text
LogoutStatus
LogoutResult
LogoutResponse
```

La ausencia de un resultado también comunica una intención:

```text
el servicio garantiza el estado final
```

# Paso 6: reutilizar el mismo hashing del refresh token

El refresh token real no debe estar almacenado en PostgreSQL.

La base ya contiene:

```text
TokenHash = SHA256(refreshToken)
```

Por tanto logout debe repetir exactamente el mismo proceso:

```text
cookie
↓
refresh token real
↓
SHA-256
↓
TokenHash
↓
buscar en DB
```

No crees un segundo algoritmo exclusivo para logout.

Reutiliza:

```csharp
private static string HashRefreshToken(
    string refreshToken)
{
    var bytes =
        Encoding.UTF8.GetBytes(refreshToken);

    var hash =
        SHA256.HashData(bytes);

    return Convert.ToHexString(hash);
}
```

La propiedad que necesitamos es el determinismo:

```text
SHA256(RT1)
↓
HASH1

SHA256(RT1)
↓
HASH1
```

Gracias a eso podemos validar y revocar el token sin persistir el secreto real.

# Paso 8: calcular el hash

Después:

```csharp
var tokenHash =
    HashRefreshToken(refreshToken);
```

Nunca hagas una consulta con:

```csharp
refreshToken == storedToken.TokenHash
```

porque son representaciones diferentes.

La comparación conceptual correcta es:

```text
token real recibido
↓
SHA-256
↓
hash calculado
↓

```

# Paso 9: buscar la sesión mediante el repositorio existente

Si tu persistencia ya tiene:


úsalo:

```csharp
var storedToken =
```

No necesitas un método:


dentro del repositorio.

Debe saber:

```text

persistir
```

# Nota sobre `Include(User)`

Es posible que `FindByHashAsync()` exista originalmente para refresh y haga:

```csharp
.Include(refreshToken => refreshToken.User)
```

porque `RefreshAsync()` necesita al usuario para emitir un nuevo JWT.

Logout probablemente no necesita esa navegación.

Podrías crear una consulta más ligera, pero no es obligatorio.

Antes de añadir:

```text
FindSessionByHashWithoutUserAsync
```

pregúntate:

```text
¿la optimización compensa un nuevo contrato?
```

Para la primera implementación suele ser mejor reutilizar el método existente y
medir antes de optimizar.

No hay nada que modificar.


# Paso 11: capturar una sola vez el tiempo actual

En lugar de hacer:

```csharp
DateTime.UtcNow
```

varias veces:

```csharp
if (storedToken.ExpiresAt <= DateTime.UtcNow)
{
    // ...
}

refreshTokenRepository.Revoke(
    storedToken,
    DateTime.UtcNow);
```

puedes capturar:

```csharp
var now = DateTime.UtcNow;
```

y reutilizarlo.

Esto mantiene una única referencia temporal durante la operación:

```csharp
var now = DateTime.UtcNow;
```

No suele cambiar el comportamiento de forma significativa, pero hace la lógica
más consistente y fácil de probar mentalmente.

---

# Paso 12: token ya revocado significa no-op

Comprueba:

```csharp
if (storedToken.RevokedAt is not null)
{
    return;
}
```

Si:

```text
RevokedAt = 2026-08-15T20:00:00Z
```

la sesión ya fue invalidada.

Volver a asignar:

```text
RevokedAt = otra fecha
```

no aporta nada y destruye información sobre cuándo ocurrió la primera
revocación.

---

# Paso 13: token expirado significa no-op

Comprueba:

```csharp
if (storedToken.ExpiresAt <= now)
{
    return;
}
```

Un token expirado ya no puede ser utilizado para renovar la sesión.

Conceptualmente:

```text
activo
──────
RevokedAt == null
AND
ExpiresAt > now
```

Por tanto:

```text
expirado
→ ya no es activo
→ no necesita revocación para cumplir logout
```

---

# ¿Debería marcar como revocados los tokens expirados?

No es necesario para este caso de uso.

Podrías decidir que toda llamada de logout escriba:

```text
RevokedAt = now
```

incluso si el token expiró.

Pero eso mezcla dos estados distintos:

```text
expiró naturalmente
```

y:

```text
fue revocado explícitamente
```

Mantenerlos separados conserva más información semántica.

---

# Paso 14: revocar únicamente una sesión activa

Si llegaste hasta aquí:

```text
storedToken != null
AND
RevokedAt == null
AND
ExpiresAt > now
```

entonces:

```csharp
refreshTokenRepository.Revoke(
    storedToken,
    now);
```

Si tu repositorio tiene:

```csharp
void Revoke(
    RefreshToken refreshToken,
    DateTime revokedAt,
    string? replacedByTokenHash = null);
```

no pases un reemplazo.

# Diferencia entre refresh y logout

Durante refresh:

```text
RT1
↓
RevokedAt = now
ReplacedByTokenHash = Hash(RT2)
```

Durante logout:

```text
RT1
↓
RevokedAt = now
ReplacedByTokenHash = null
```

¿Por qué?

Refresh continúa la cadena:

```text
RT1 → RT2
```

Logout termina la cadena:

```text
RT1 → fin
```

Esto hace que los datos persistidos sean interpretables después.

# Paso 16: implementación completa del servicio

Una versión simple:

```csharp
public async Task LogoutAsync(
    string? refreshToken,
    CancellationToken cancellationToken = default)
{
    if (string.IsNullOrWhiteSpace(refreshToken))
    {
        return;
    }

    var tokenHash =
        HashRefreshToken(refreshToken);

    var storedToken =
        await refreshTokenRepository.FindByHashAsync(
            tokenHash,
            cancellationToken);

    if (storedToken is null)
    {
        return;
    }

    var now = DateTime.UtcNow;

    if (storedToken.RevokedAt is not null ||
        storedToken.ExpiresAt <= now)
    {
        return;
    }

    refreshTokenRepository.Revoke(
        storedToken,
        now);

    await refreshTokenRepository.SaveChangesAsync(
        cancellationToken);
}
```

La lógica se puede leer como:

```text
¿hay token?
↓
sí

¿existe sesión?
↓
sí

¿está activa?
↓
sí

revocar
↓
guardar
```

Todo lo demás es no-op.

# Paso 20: eliminar siempre la cookie

# Paso 21: entender cómo se identifica una cookie

Para poder eliminar una cookie de forma fiable, recuerda que su identidad está
ligada principalmente a:

```text
Name
Domain
Path
```

Por ejemplo, si fue creada con:

```csharp
Path = "/api/auth";
```

y después intentas borrarla con:

```csharp
Path = "/";
```

puedes terminar actuando sobre una cookie diferente.

Por eso conviene centralizar la configuración.

Por ejemplo:

```csharp
private const string RefreshTokenCookieName =
    "myapp.refreshToken";
```

y reutilizar el mismo `Path`.

Si configuraste explícitamente `Domain`, también debe coincidir al eliminarla.

---

# Paso 22: mantener un helper para borrar la cookie

Ejemplo:

```csharp
private static void DeleteRefreshTokenCookie(
    HttpResponse response)
{
    response.Cookies.Delete(
        RefreshTokenCookieName,
        new CookieOptions
        {
            Path = "/api/auth"
        });
}
```

Si tu aplicación utiliza `Domain`, inclúyelo también en las opciones de
eliminación.

La idea es evitar duplicar strings como:

```text
"myapp.refreshToken"
"/api/auth"
```

en múltiples lugares.

# `HttpOnly`, `Secure` y `SameSite` durante logout

Al crear la cookie quizá utilizaste:


Estas opciones siguen siendo fundamentales para la seguridad y el transporte de

Pero, para encontrar la cookie que quieres eliminar, presta especial atención a:

```text

```

Centralizar los helpers de creación y eliminación reduce inconsistencias.

# Paso 23: implementar el handler completo

```csharp
private static async Task<NoContent> LogoutAsync(
    HttpRequest request,
    HttpResponse response,
    IAuthService authService,
    CancellationToken cancellationToken)
{
    request.Cookies.TryGetValue(
        RefreshTokenCookieName,
        out var refreshToken);

    await authService.LogoutAsync(
        refreshToken,
        cancellationToken);

    DeleteRefreshTokenCookie(response);

    return TypedResults.NoContent();
}
```

El flujo queda:

```text
request
↓
leer cookie
↓
Application intenta revocar
↓
eliminar cookie
↓
204
```


No generes una migración si no cambiaste el modelo EF Core.

# Paso 25: no crear una blacklist de JWT por accidente

Esta feature no requiere:

```text
AccessTokenBlacklist

```

El modelo sigue siendo:

```text
JWT
↓
válido hasta expirar


Refresh Token
↓
revocable en DB
```

Agregar una blacklist puede ser válido en sistemas con requisitos más estrictos,
pero cambia el diseño y debe ser una decisión separada.

# Paso 26: implementar el request de logout en frontend

Ahora pasamos al cliente.

Si ya tienes:

```typescript
login()
register()
refresh()
```

dentro de:

```text
authService.ts
```

agrega:

```typescript
export async function logout(): Promise<void> {
  await apiClient.post("/auth/logout");
}
```

No necesitas:

```typescript
return response.data;
```

porque el servidor responde:

```http
204 No Content
```

Por eso el tipo natural es:

```typescript
Promise<void>
```

# Paso 27: no enviar el refresh token desde React

```typescript
apiClient.post("/auth/logout", {
```

Ni:


```text

```

JavaScript no puede leerlo.

La petición debe ser simplemente:

```typescript
await apiClient.post("/auth/logout");
```

# Paso 29: mantener `AuthContext.logout()` local

Un `AuthProvider` puede tener:

```typescript
const logout = useCallback(() => {
  setAccessToken(null);
  setUser(null);
```

Conserva esa función simple.

No hagas directamente:

# ¿Por qué no meter Axios dentro de `AuthProvider`?

Porque el provider tiene una responsabilidad clara:

```text
AuthProvider
────────────
estado React
```

Si añades:

```text
HTTP
```

empieza a convertirse en:

```text
state manager
+
API service
+
session coordinator
```

También puede existir código interno, como el interceptor, que necesite:

```typescript
logout();
```

solamente para limpiar el estado local cuando una sesión ya es irrecuperable.

En ese caso no quieres necesariamente iniciar otra petición `/logout`.

# Paso 30: distinguir logout local y logout remoto

Esta separación es fundamental.

## Logout remoto

```typescript
authService.logout()
```

significa:

```text
pedir al servidor que invalide la sesión renovable
```

## Logout local

```typescript
AuthContext.logout()
```

significa:

```text
eliminar accessToken y user del runtime React
```

## Logout completo

Necesitamos una pequeña capa que coordine:

```text
remoto
+
local
```

# Paso 31: crear `useLogout`

Una opción sencilla:

```typescript
import { useCallback } from "react";
import { useAuth } from "./useAuth";
import {
  logout as logoutRequest,
} from "../services/authService";

export function useLogout() {
  const {
    logout: clearLocalSession,
  } = useAuth();

  return useCallback(async () => {
    try {
      await logoutRequest();
    } finally {
      clearLocalSession();
    }
  }, [clearLocalSession]);
}
```

Este hook representa el caso de uso completo desde el frontend.

# Paso 32: entender el `try/finally`

Esta decisión merece atención.

```typescript
try {
  await logoutRequest();
} finally {
  clearLocalSession();
}
```

significa:

```text
backend responde 204
↓
limpiar estado local
```

pero también:

```text
network error
↓
limpiar estado local
```

---

# ¿Por qué limpiar localmente si el request falla?

Porque el usuario pidió salir de la sesión en ese cliente.

Mantener:

```text
accessToken
user
isAuthenticated = true
```

después de pulsar logout solamente porque hubo un error de red puede ser
sorprendente.

`finally` garantiza:

```text
estado local
→ no autenticado
```

---

# Pero existe una consecuencia importante

Si la petición falla antes de llegar al servidor:

```text
Frontend
────────
accessToken eliminado
user eliminado


Backend
───────
refresh token quizá sigue activo


Browser
───────
cookie quizá sigue presente
```

Por eso no debes ocultar el error.

Con:

```typescript
try {
  await logoutRequest();
} finally {
  clearLocalSession();
}
```

la excepción continúa propagándose.

Así una capa superior puede decidir:

```text
mostrar error
registrar telemetría
reintentar
informar al usuario
```

sin conservar el estado autenticado local.

# Paso 33: no usar un `catch` vacío

Evita:

```typescript
try {
  await logoutRequest();
} catch {
  // ignorado
}

clearLocalSession();
```

porque escondería:

```text
"el backend quizá no revocó la sesión"
```

La diferencia entre:

```text
limpiar estado local
```

y:

```text
confirmar revocación remota
```

debe seguir siendo observable para quien consume el hook.

# Paso 35: mantener `/auth/logout` fuera del refresh automático

Si utilizas un response interceptor que reacciona a `401`, excluye endpoints de
autenticación:

```typescript
const REFRESH_EXCLUDED_ENDPOINTS = [
  "/auth/login",
  "/auth/register",
  "/auth/refresh",
  "/auth/logout",
];
```

Logout no debe provocar:

```text
/logout
↓
401
↓
/refresh
↓
renovar sesión
```

Eso sería conceptualmente contrario a la intención del usuario.

La regla es:

> **Nunca intentes restaurar automáticamente una sesión mientras estás
> intentando destruirla.**

# Paso 36: entender por qué el request interceptor no rompe logout

Es posible que tu request interceptor haga:

```typescript
if (accessTokenRef.current) {
  config.headers.set(
    "Authorization",
    `Bearer ${accessTokenRef.current}`,
  );
}
```

Por tanto `/logout` puede llegar con un Bearer token si aún existe.

Eso no es un problema.

El punto importante es que backend **no dependa** de ese JWT para autorizar el
logout.

La sesión a revocar se identifica por la cookie.

# Paso 37: CORS y cookies cross-origin

Si frontend y backend viven en orígenes distintos:

```text
https://app.example.com
https://api.example.com
```

el cliente puede necesitar:

```typescript
withCredentials: true
```

y el backend:

```csharp
policy
    .WithOrigins(allowedOrigins)
    .AllowAnyHeader()
    .AllowAnyMethod()
    .AllowCredentials();
```

No combines:

```csharp
AllowAnyOrigin()
```

con credenciales.

También revisa la política de cookie:

```text
Secure
SameSite
Domain
Path
```

según tu arquitectura real.

Logout no puede revocar una cookie que el navegador nunca envía.

# Errores comunes

| Error | Consecuencia | Solución |
|---|---|---|
| Limpiar solamente React | El refresh token puede seguir activo | Revocar también la sesión en backend |
| Exigir JWT válido en `/logout` | Usuario no puede cerrar sesión después de expirar el access token | Permitir logout basado en refresh cookie |
| Devolver 401 si no hay cookie | Logout deja de ser idempotente | Responder 204 |
| Persistir refresh token real | Robo de DB expone sesiones utilizables | Guardar solamente SHA-256 |
| Crear un hash diferente para logout | No se encuentra la sesión | Reutilizar el mismo hashing |
| Crear un token reemplazo durante logout | La sesión continúa | `ReplacedByTokenHash = null` |
| No eliminar la cookie | Navegador conserva una credencial inútil o potencialmente activa | Borrarla siempre |
| Borrar con `Path` distinto | La cookie original puede permanecer | Reutilizar nombre/path/domain |
| Meter Axios en `AuthProvider` | Estado y transporte quedan acoplados | Mantener logout local separado |
| Guardar refresh token en Context | JavaScript obtiene acceso al secreto | Mantenerlo HttpOnly |
| Hacer `catch {}` en frontend | Se oculta un fallo de revocación remota | Usar `finally` y propagar el error |
| Permitir refresh automático sobre `/logout` | Posibles loops o renovación durante cierre | Excluir auth endpoints |
| Agregar JWT blacklist sin requerimiento | Mayor complejidad y estado por request | Mantener JWT corto y stateless |
| Generar migración sin cambios de modelo | Ruido y riesgo innecesario | No migrar |
| Mezclar navegación con `AuthProvider` | Context queda acoplado al router | Navegar desde UI/guards |
