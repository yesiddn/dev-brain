# Antes de empezar: la decisión arquitectónica

Una arquitectura típica utiliza:

```text
Access Token
    ↓
JWT
    ↓
corta duración
    ↓
stateless

Refresh Token
    ↓
valor aleatorio opaco
    ↓
larga duración
    ↓
stateful
```

Ejemplo conceptual:

```text
Login
 │
 ├── Access Token JWT
 │      └── 15 minutos, por ejemplo
 │
 └── Refresh Token opaco
        └── varios días o semanas
```

El access token demuestra:

```text
"Este usuario está autorizado durante un período corto."
```

El refresh token representa:

```text
"Esta sesión puede solicitar nuevas credenciales."
```

Son responsabilidades diferentes y por eso no necesitan tener el mismo formato.

---

# Paso 1: No utilizar otro JWT solamente porque ya usamos JWT

Una pregunta común al implementar refresh tokens es:

> ¿Por qué no generar simplemente otro JWT con una expiración mayor?

Técnicamente es posible.

Podrías tener:

```text
Access JWT
└── exp = 15 minutos

Refresh JWT
└── exp = 30 días
```

Pero que sea posible no significa que sea necesariamente la opción más conveniente.

---

## Problema conceptual

El beneficio principal de un JWT es que puede ser validado sin consultar estado en el servidor.

```text
JWT
 ↓
validar firma
 ↓
validar exp
 ↓
leer claims
 ↓
aceptar
```

Eso funciona muy bien para access tokens de corta duración.

Pero un refresh token normalmente necesita responder:

```text
¿Fue revocado?

¿Ya fue utilizado?

¿Fue reemplazado?

¿Esta sesión sigue habilitada?

¿El usuario cerró sesión?

¿Este token pertenece a una cadena de rotación comprometida?
```

En cuanto necesitás responder esas preguntas, necesitás estado en el servidor.

Entonces incluso utilizando un JWT como refresh token probablemente terminarías consultando la base de datos.

El JWT deja de aportar gran parte de su principal beneficio.

---

## Alternativa recomendada

Usar:

```text
valor aleatorio criptográficamente seguro
```

Por ejemplo:

```text
TBBUpIdAwzp4pOon9EMKBSGJyOmGF3GUYdo0-FWPkWU
```

El token no contiene:

```text
UserId
Email
Roles
Claims
Expiration
Issuer
Audience
```

No significa nada por sí solo.

Por eso se denomina:

```text
opaque token
```

u:

```text
token opaco
```

---

# Paso 2: Entender qué significa "opaco"

Un token opaco es simplemente un valor cuya estructura interna no tiene significado para el cliente.

Por ejemplo:

```text
TBBUpIdAwzp4pOon9EMKBSGJyOmGF3GUYdo0-FWPkWU
```

No podés decodificarlo y obtener:

```json
{
  "sub": "...",
  "email": "...",
  "exp": "..."
}
```

Es únicamente:

```text
una credencial secreta aleatoria
```

Su significado está del lado del servidor:

```text
token
  ↓
hash(token)
  ↓
RefreshTokens.TokenHash
  ↓
UserId
ExpiresAt
RevokedAt
...
```

Esto es parecido conceptualmente a una llave.

La llave no necesita contener los datos de la casa.

Solo necesita ser imposible de adivinar y permitir identificar qué acceso representa.

---

# Paso 3: ¿Qué significa "un valor aleatorio de 256 bits"?

Cuando hablamos de un refresh token aleatorio de:

```text
256 bits
```

estamos hablando de la cantidad de **entropía aleatoria** utilizada para construirlo.

Recordá:

```text
8 bits = 1 byte
```

Entonces:

```text
256 bits / 8 = 32 bytes
```

Por eso generaremos:

```csharp
32 bytes aleatorios
```

---

## No significa que el string tenga 256 caracteres

Esto es importante.

Tenemos:

```text
32 bytes aleatorios
```

Internamente:

```text
256 bits
```

Pero después necesitamos convertir esos bytes a texto para transportarlos por HTTP.

Por ejemplo:

```text
32 bytes
   ↓
Base64URL
   ↓
aproximadamente 43 caracteres
```

Entonces algo como:

```text
JSSIvE2GeA6waBJMeQEPSVzcxlZG9Ac0smTdTuCGHjs
```

puede representar perfectamente 256 bits de aleatoriedad aunque tenga solamente unos 43 caracteres.

---

# Paso 4: ¿Por qué 256 bits?

Un refresh token funciona como una credencial.

Si alguien lo conoce, potencialmente puede utilizarlo para obtener un nuevo access token.

Por eso necesitamos que sea extremadamente difícil de adivinar.

Con 256 bits existen:

```text
2^256
```

posibles valores.

Aproximadamente:

```text
1.15 × 10^77
```

posibilidades.

No intentamos hacer que el token:

```text
parezca complicado
```

Intentamos hacer que sea:

```text
criptográficamente impredecible
```

---

# Paso 5: Nunca utilizar `Random`

No hagas:

```csharp
var random = new Random();
```

ni construyas un token usando:

```csharp
random.Next()
```

`System.Random` está diseñado para:

```text
simulaciones;
juegos;
valores pseudoaleatorios generales.
```

No para generar secretos.

Para seguridad necesitamos un:

```text
CSPRNG
```

que significa:

```text
Cryptographically Secure
Pseudo-Random Number Generator
```

En .NET utilizamos:

```csharp
System.Security.Cryptography.RandomNumberGenerator
```

---

# Paso 6: Generar 32 bytes aleatorios

.NET permite hacerlo directamente:

```csharp
using System.Security.Cryptography;

byte[] bytes = RandomNumberGenerator.GetBytes(32);
```

Ahora:

```text
bytes.Length = 32
```

y:

```text
32 bytes × 8 bits = 256 bits
```

Ese es el material criptográfico del refresh token.

---

# Paso 7: Convertir los bytes a Base64URL

Los bytes binarios no son cómodos para:

```text
cookies;
JSON;
URLs;
headers;
logs de desarrollo.
```

Por eso necesitamos una representación textual.

Una opción natural es:

```text
Base64URL
```

---

## Base64 tradicional

Un Base64 convencional puede contener:

```text
A-Z
a-z
0-9
+
/
=
```

Por ejemplo:

```text
xE7/8tzZKyY+4g==
```

Los caracteres:

```text
+
/
=
```

pueden ser incómodos en algunos contextos HTTP y URLs.

---

## Base64URL

Base64URL adapta Base64 utilizando:

```text
- en lugar de +
_ en lugar de /
```

y normalmente elimina:

```text
=
```

del padding final.

Ejemplo:

```text
JSSIvE2GeA6waBJMeQEPSVzcxlZG9Ac0smTdTuCGHjs
```

Es más cómodo para tokens.

---

# Paso 8: Implementar la codificación Base64URL

Dependiendo de la versión y librerías utilizadas por el proyecto, podés encapsular la conversión.

Por ejemplo:

```csharp
private static string ToBase64Url(byte[] bytes)
{
    return Convert
        .ToBase64String(bytes)
        .TrimEnd('=')
        .Replace('+', '-')
        .Replace('/', '_');
}
```

Ahora:

```csharp
var bytes = RandomNumberGenerator.GetBytes(32);

var token = ToBase64Url(bytes);
```

Flujo:

```text
RandomNumberGenerator
        ↓
     32 bytes
        ↓
     256 bits
        ↓
    Base64URL
        ↓
refresh token real
```

---

# Paso 9: Crear un generador reusable

No queremos tener esto repetido dentro del login:

```csharp
RandomNumberGenerator.GetBytes(...)
```

Podemos encapsular la responsabilidad.

Por ejemplo:

```csharp
public interface IRefreshTokenGenerator
{
    string Generate();
}
```

Implementación:

```csharp
using System.Security.Cryptography;

public sealed class RefreshTokenGenerator
    : IRefreshTokenGenerator
{
    private const int TokenSizeInBytes = 32;

    public string Generate()
    {
        var bytes = RandomNumberGenerator.GetBytes(
            TokenSizeInBytes);

        return Convert
            .ToBase64String(bytes)
            .TrimEnd('=')
            .Replace('+', '-')
            .Replace('/', '_');
    }
}
```

Ahora el resto de la aplicación simplemente conoce:

```csharp
var refreshToken = _refreshTokenGenerator.Generate();
```

No necesita saber cómo se genera.

# Paso 10: Registrar el generador en DI

Por ejemplo:

```csharp
services.AddSingleton<
    IRefreshTokenGenerator,
    RefreshTokenGenerator>();
```

El generador:

```text
no tiene estado;
no usa DbContext;
no depende de una request.
```

Por eso puede ser `Singleton`.

También podría ser `Transient` sin cambiar el comportamiento.

# Paso 11: El token generado NO debe persistirse directamente

Supongamos que generamos:

```text
JSSIvE2GeA6waBJMeQEPSVzcxlZG9Ac0smTdTuCGHjs
```

Ese valor será entregado al cliente.

Pero la base de datos no debería almacenar:

```text
TokenHash
───────────────────────────────────────────
JSSIvE2GeA6waBJMeQEPSVzcxlZG9Ac0smTdTuCGHjs
```

Necesitamos transformar el token antes de persistirlo.

Aquí entra:

```text
SHA-256
```

# SHA-256: explicación conceptual

Antes de escribir código es importante entender qué estamos haciendo.

---

## ¿Qué es SHA-256?

SHA-256 significa:

```text
Secure Hash Algorithm 256-bit
```

Es una función hash criptográfica perteneciente a la familia SHA-2.

Conceptualmente recibe:

```text
entrada de cualquier tamaño
```

y produce:

```text
256 bits
```

de salida.

Es decir:

```text
Input
   ↓
SHA-256
   ↓
32 bytes
```

Siempre.

---

## Ejemplo conceptual

Tenemos:

```text
hello
```

Aplicamos:

```text
SHA256("hello")
```

y obtenemos un valor fijo de 256 bits.

Si utilizamos hexadecimal para mostrar esos bytes tendremos:

```text
64 caracteres hexadecimales
```

porque:

```text
1 carácter hexadecimal = 4 bits
```

Entonces:

```text
256 / 4 = 64
```

---

# Propiedad 1: SHA-256 es determinístico

La misma entrada produce siempre la misma salida.

```text
SHA256("token-A")
        ↓
hash-X

SHA256("token-A")
        ↓
hash-X
```

Esto es precisamente lo que necesitamos.

Cuando el usuario vuelva posteriormente con su refresh token:

```text
token-A
```

podemos calcular otra vez:

```text
SHA256(token-A)
```

y buscar:

```text
TokenHash = hash-X
```

en PostgreSQL.

---

# Propiedad 2: pequeños cambios producen hashes completamente diferentes

Por ejemplo:

```text
token-A
token-B
```

aunque sean muy parecidos como texto, sus hashes serán completamente diferentes.

Conceptualmente:

```text
token-A
   ↓
2F32A8...

token-B
   ↓
9C41E7...
```

Esto se conoce como:

```text
avalanche effect
```

Un cambio pequeño en la entrada provoca un cambio importante en la salida.

---

# Propiedad 3: SHA-256 es unidireccional

SHA-256 no es cifrado.

Esto es muy importante.

Con cifrado:

```text
plaintext
   ↓ encrypt(key)
ciphertext
   ↓ decrypt(key)
plaintext
```

Existe una operación inversa.

Con hashing:

```text
token
  ↓
SHA-256
  ↓
hash
```

no existe:

```text
SHA256.Decrypt(hash)
```

El algoritmo no está diseñado para recuperar la entrada original.

---

# Hashing no es encryption

No confundas:

```text
hash
```

con:

```text
encrypted value
```

Una base de datos puede almacenar:

```text
TokenHash
```

sin que la aplicación necesite volver a obtener el token original.

Eso funciona porque la validación utiliza:

```text
comparación de hashes
```

y no recuperación del secreto.

---

# Paso 12: ¿Por qué SHA-256 es apropiado para refresh tokens?

Alguien podría preguntar:

> ¿No deberían utilizarse bcrypt, Argon2 o PBKDF2?

Para contraseñas, sí.

Para refresh tokens aleatorios de alta entropía, normalmente no es necesario.

La diferencia está en la entrada.

---

## Contraseña humana

Una contraseña como:

```text
perrito123
```

tiene relativamente poca entropía.

Un atacante puede probar:

```text
password
password123
123456
perrito
perrito123
...
```

Por eso los passwords necesitan funciones deliberadamente costosas como:

```text
Argon2
bcrypt
PBKDF2
scrypt
```

para hacer los ataques de fuerza bruta más lentos.

---

## Refresh token

Nuestro refresh token tiene:

```text
256 bits aleatorios
```

No fue inventado por un humano.

No viene de un diccionario.

Un atacante no puede realizar razonablemente:

```text
dictionary attack
```

contra él.

Tendría que encontrar uno de:

```text
2^256
```

valores posibles.

Por eso un hash rápido como SHA-256 es apropiado para este tipo de secreto aleatorio.

---

# ¿Necesitamos salt?

Normalmente no para este caso.

Un `salt` es especialmente importante para contraseñas porque usuarios diferentes pueden utilizar exactamente la misma contraseña.

Sin salt:

```text
SHA256("password123")
```

sería igual para todos.

Pero nuestros refresh tokens ya son:

```text
aleatorios;
únicos;
de alta entropía.
```

Dos usuarios no deberían compartir el mismo token.

Además necesitamos poder hacer:

```text
WHERE TokenHash = ...
```

fácilmente.

Por eso un hash determinístico es conveniente.

---

# Importante: SHA-256 no convierte un token débil en uno fuerte

Esto sería incorrecto:

```text
token = Guid.NewGuid().ToString()
hash = SHA256(token)
```

y concluir:

```text
"Ahora tengo seguridad de 256 bits porque SHA-256 produce 256 bits."
```

La seguridad depende principalmente de la entropía de la entrada.

Si una entrada solo tuviera:

```text
64 bits de entropía
```

hacer:

```text
SHA256(input)
```

no crea mágicamente:

```text
256 bits de entropía
```

Por eso primero hacemos:

```text
RandomNumberGenerator.GetBytes(32)
```

y después:

```text
SHA-256
```

Las dos operaciones cumplen responsabilidades diferentes.

---

# Modelo mental: random y hash no hacen lo mismo

```text
RandomNumberGenerator
        ↓
crea el secreto

SHA-256
        ↓
crea una representación segura
para almacenarlo
```

En otras palabras:

```text
RNG → seguridad del token

SHA-256 → protección en persistencia
```

---

# Paso 13: Implementar SHA-256 en .NET

.NET proporciona:

```csharp
SHA256.HashData(...)
```

Primero convertimos el token a bytes UTF-8:

```csharp
Encoding.UTF8.GetBytes(token)
```

Después:

```csharp
SHA256.HashData(bytes)
```

Ejemplo:

```csharp
using System.Security.Cryptography;
using System.Text;

var tokenBytes = Encoding.UTF8.GetBytes(refreshToken);

var hashBytes = SHA256.HashData(tokenBytes);
```

`hashBytes` contiene:

```text
32 bytes
```

porque SHA-256 siempre devuelve:

```text
256 bits
```

```csharp
var tokenHash = Convert.ToHexString(hashBytes);
```

Flujo:

```text
Refresh token real
      ↓
Encoding.UTF8
      ↓
bytes
      ↓
SHA256.HashData
      ↓
32-byte hash
      ↓
Convert.ToHexString
      ↓
64 caracteres
```

Ejemplo conceptual:

```text
0F5CD15A3E...
```

# Paso 15: Crear un servicio de hashing reusable

Podemos encapsular esta operación:

```csharp
public interface IRefreshTokenHasher
{
    string Hash(string refreshToken);
}
```

Implementación:

```csharp
using System.Security.Cryptography;
using System.Text;

public sealed class RefreshTokenHasher
    : IRefreshTokenHasher
{
    public string Hash(string refreshToken)
    {
        var tokenBytes = Encoding.UTF8.GetBytes(
            refreshToken);

        var hashBytes = SHA256.HashData(
            tokenBytes);

        return Convert.ToHexString(hashBytes);
    }
}
```

Uso:

```csharp
var tokenHash = _refreshTokenHasher.Hash(
    refreshToken);
```

Si utilizás exactamente:

```csharp

    SHA256.HashData(...))
```

el resultado siempre tiene:

```text

```

Entonces podrías utilizar:

```csharp

```

en EF Core.

Si tu playbook de persistencia utiliza:



Lo importante es que la decisión sea consciente.

# Paso 17: Separar tres valores mentalmente

Durante el flujo vamos a manejar tres conceptos distintos.

### 1. Bytes aleatorios

```text
32 bytes
```

Solo existen durante la generación.

---

### 2. Refresh token real

```text
Base64URL(random bytes)
```

Ejemplo:

```text
JSSIvE2GeA6waBJMeQEPSVzcxlZG9Ac0smTdTuCGHjs
```

Este valor:

```text
lo recibe el cliente;
debe tratarse como secreto.
```

---

### 3. TokenHash

```text
SHA256(refresh token real)
```

Ejemplo:

```text
89EC4A890...
```

Este valor:

```text
se almacena en PostgreSQL.
```

Nunca confundas los tres.

# Paso 19: Crear una operación que genere token + hash

Podemos encapsular ambas cosas en un resultado.

Por ejemplo:

```csharp
public sealed record GeneratedRefreshToken(
    string Token,
    string Hash);
```

Servicio:

```csharp
public interface IRefreshTokenService
{
    GeneratedRefreshToken Generate();
}
```

Implementación conceptual:

```csharp
public sealed class RefreshTokenService(
    IRefreshTokenGenerator tokenGenerator,
    IRefreshTokenHasher tokenHasher)
    : IRefreshTokenService
{
    public GeneratedRefreshToken Generate()
    {
        var token = tokenGenerator.Generate();

        var hash = tokenHasher.Hash(token);

        return new GeneratedRefreshToken(
            token,
            hash);
    }
}
```

Ahora:

```csharp
var generatedToken =
    _refreshTokenService.Generate();
```

produce:

```text
generatedToken.Token
    → cliente

generatedToken.Hash
    → database
```

# Paso 20: Nunca devolver el hash al cliente

La responsabilidad debe mantenerse clara.

El cliente recibe:

```text
Token
```

PostgreSQL recibe:

```text
Hash
```

No al revés.

Incorrecto:

```json
{
  "refreshTokenHash": "ABCD..."
}
```

Correcto conceptualmente:

```text
Cookie:
refreshToken=<TOKEN REAL>
```

La aplicación nunca necesita exponer:

```text
TokenHash
```

al cliente.

# Paso 24: ¿Por qué `HttpOnly`?

Una cookie:

```text
HttpOnly
```

no puede ser leída directamente desde JavaScript.

Por ejemplo:

```javascript
document.cookie;
```

no debería poder recuperar esa cookie.

Esto reduce la exposición del refresh token frente a determinados ataques XSS.

# Paso 25: ¿Por qué `Secure`?

```text
Secure = true
```

indica que la cookie debe enviarse mediante HTTPS.

Un refresh token es una credencial sensible.

No debería viajar por conexiones HTTP sin cifrar.

# Paso 26: ¿Qué hace `SameSite`?

`SameSite` controla cuándo el navegador envía una cookie durante solicitudes originadas desde otros sitios.

Los valores principales son:

```text
Strict
Lax
None
```

La elección depende de la arquitectura frontend/backend.

Por ejemplo:

```text
SPA y API mismo site
```

puede permitir políticas más estrictas.

Mientras:

```text
frontend y backend en contextos cross-site
```

puede requerir:

```text
SameSite=None
Secure=true
```

No copies una configuración de `SameSite` sin comprender cómo están desplegados frontend y backend.

# Paso 36: ¿Qué es rotación?

Supongamos:



# Paso 48: Algoritmo completo de `/refresh`

Mentalmente:


# Paso 49: Ejemplo simplificado del servicio

Una implementación conceptual podría verse así:

```csharp
public async Task<RefreshResult?> RefreshAsync(
    string refreshToken,
    CancellationToken cancellationToken = default)
{
    var tokenHash =
        _refreshTokenHasher.Hash(refreshToken);

    var storedToken =
        await _refreshTokenRepository.FindByHashAsync(
            tokenHash,
            cancellationToken);

    if (storedToken is null)
    {
        return null;
    }

    var now = DateTime.UtcNow;

    if (storedToken.ExpiresAt <= now)
    {
        return null;
    }

    if (storedToken.RevokedAt is not null)
    {
        return null;
    }

    var replacement =
        _refreshTokenService.Generate();

    var newRefreshToken = new RefreshToken
    {
        Id = Guid.NewGuid(),
        UserId = storedToken.UserId,
        TokenHash = replacement.Hash,
        ExpiresAt = now.AddDays(30)
    };

    _refreshTokenRepository.Revoke(
        storedToken,
        now,
        replacement.Hash);

    await _refreshTokenRepository.AddAsync(
        newRefreshToken,
        cancellationToken);

    await _refreshTokenRepository.SaveChangesAsync(
        cancellationToken);

    var accessToken =
        _accessTokenGenerator.Generate(
            storedToken.User);

    return new RefreshResult(
        accessToken,
        replacement.Token,
        newRefreshToken.ExpiresAt);
}
```

La implementación real dependerá de dónde cargues:

```text
User
Roles
Permissions
Claims
```

```csharp

public async Task<IActionResult> Refresh(
    CancellationToken cancellationToken)
{
    if (!Request.Cookies.TryGetValue(
        "refreshToken",
        out var refreshToken))
    {
        return Unauthorized();

            result.RefreshTokenExpiresAt));

    {
        accessToken = result.AccessToken
    });
}
```

# Paso 56: Qué SHA-256 NO protege

Hashing no soluciona todos los problemas.

Si un atacante obtiene directamente:

```text

un log que contiene el token;
una request capturada;
```

entonces ya posee el secreto real.

SHA-256 protege principalmente:

```text

```

Por eso también necesitamos:

```text

HttpOnly
Secure
protección XSS

no loguear secretos

```

La seguridad se construye por capas.

# Paso 58: Detección de reutilización

Una implementación más avanzada puede distinguir:

```text

```

de:

```text

```

```text

```


Eso podría significar:

```text

el cliente antiguo todavía lo posee;
```

```text

 ↓
```

Resultado esperado:

# Errores comunes

| Error                                          | Por qué está mal                                       | Solución                                             |
| ---------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| Usar otro JWT como refresh token sin necesidad | Añade complejidad sin eliminar la necesidad de estado  | Preferir token opaco aleatorio                       |
| Utilizar `Random`                              | No es criptográficamente seguro                        | `RandomNumberGenerator`                              |
| Confundir 256 bits con 256 caracteres          | Bits representan entropía, no longitud textual         | 32 bytes = 256 bits                                  |
| Generar menos entropía y luego usar SHA-256    | Hashing no crea entropía                               | Generar 32 bytes aleatorios primero                  |
| Guardar token real                             | Una fuga de DB expone sesiones activas                 | Persistir SHA-256                                    |
| Pensar que SHA-256 cifra                       | No existe decrypt                                      | Comparar hashes                                      |
| Usar bcrypt para token aleatorio sin necesidad | Añade costo innecesario                                | SHA-256 es suficiente para secretos de alta entropía |
| Utilizar SHA-256 directamente para passwords   | Passwords tienen poca entropía                         | Argon2/bcrypt/PBKDF2                                 |
| Devolver `TokenHash` al frontend               | No aporta nada y mezcla responsabilidades              | Cliente recibe token real                            |
| Guardar refresh token en `localStorage`        | Mayor exposición ante JavaScript/XSS                   | Cookie HttpOnly                                      |
| Loguear el token                               | Los logs se convierten en almacenamiento de secretos   | Nunca registrar credenciales                         |
| Reutilizar indefinidamente el mismo token      | Un token robado conserva utilidad durante mucho tiempo | Rotación                                             |
| Rotar pero no revocar el anterior              | Dos tokens continúan funcionando                       | Revocar A al crear B                                 |
| Revocar A y guardar antes de crear B           | Puede romper la sesión ante un fallo                   | Un único `SaveChanges`                               |
| Renovar un token expirado                      | La expiración deja de tener sentido                    | 401                                                  |
| Renovar un token revocado                      | Rompe la revocación                                    | 401                                                  |
| Crear blacklist JWT automáticamente            | Mezcla access y refresh tokens                         | Mantener access token stateless                      |
| Configurar `SameSite` copiando ejemplos        | Depende del despliegue                                 | Analizar frontend/API                                |

# Preguntas frecuentes

## ¿El refresh token es un JWT?

No necesariamente.

En este diseño:

```text
Access Token = JWT
Refresh Token = opaque random token
```

---

## ¿Por qué 32 bytes?

Porque:

```text
32 × 8 = 256 bits
```

de entropía aleatoria.

---

## ¿Por qué Base64URL?

Porque necesitamos representar bytes aleatorios como texto de forma compacta y cómoda para HTTP.

---

## ¿Base64URL agrega seguridad?

No.

Base64URL es:

```text
encoding
```

no:

```text
encryption
```

La seguridad proviene de:

```text
RandomNumberGenerator
```

---

## ¿SHA-256 agrega aleatoriedad?

No.

SHA-256 transforma una entrada en un digest de 256 bits.

La entropía viene de:

```text
RandomNumberGenerator.GetBytes(32)
```

---

## ¿Por qué almacenar SHA-256?

Para que una filtración de PostgreSQL no revele directamente los refresh tokens utilizables.

---

## ¿Por qué podemos buscar el hash?

Porque SHA-256 es determinístico.

```text
SHA256(Token A) = Hash A
```

siempre.

---

## ¿Por qué no necesitamos recuperar el token desde el hash?

Porque el servidor nunca necesita recuperar el token original.

El cliente presenta el original.

El servidor calcula:

```text
SHA256(original)
```

y compara.

---

## ¿Por qué SHA-256 y no bcrypt?

Porque bcrypt está diseñado principalmente para secretos de baja entropía, especialmente passwords humanos.

Nuestro token tiene:

```text
256 bits aleatorios
```

y no es vulnerable a ataques prácticos de diccionario.

---

## ¿Necesita salt?

Normalmente no para un token aleatorio de alta entropía utilizado como identificador secreto y buscado por hash.

Los propios tokens ya son valores aleatorios únicos.

---

## ¿Puede haber colisiones SHA-256?

Matemáticamente cualquier función con salida finita puede tener colisiones.

Pero con SHA-256 la probabilidad relevante para este caso es tan pequeña que no representa una preocupación práctica.

Además el índice único protege el modelo de persistencia.

---

## ¿Por qué rotar?

Para limitar el tiempo durante el cual un refresh token capturado continúa siendo útil.

Después de utilizar A:

```text
A → revoked
B → active
```

---

## ¿Por qué conservar `ReplacedByTokenHash`?

Para poder reconstruir:

```text
A → B → C
```

y posteriormente implementar detección de reutilización y revocación de familias de tokens.

# Modelo mental definitivo

Si dentro de seis meses olvidás la implementación, recordá solamente esto:

```text
GENERAR
───────

RandomNumberGenerator.GetBytes(32)
            ↓
        256 bits
            ↓
        Base64URL
            ↓
      TOKEN REAL
       ↙       ↘
 cliente      SHA-256
                 ↓
             TOKEN HASH
                 ↓
                 DB
```

Cuando vuelve el cliente:

```text
VALIDAR
───────

TOKEN REAL
    ↓
SHA-256
    ↓
TOKEN HASH
    ↓
buscar en DB
    ↓
existe?
    ↓
no expiró?
    ↓
no revocado?
```

Si es válido:

```text
ROTAR
─────

Token A
   ↓
generar B
   ↓
revocar A
   ↓
A.ReplacedByTokenHash = Hash(B)
   ↓
guardar B
   ↓
SaveChanges
   ↓
cliente recibe B
```

La idea central es:

> **El refresh token real es una credencial aleatoria que solamente posee el cliente. El servidor no necesita conocer su valor permanentemente: necesita poder reconocerlo cuando regrese. SHA-256 permite reconocerlo sin persistir el secreto original.**

Y la distinción más importante de todas:

```text
RandomNumberGenerator
    → crea el secreto.

Base64URL
    → representa el secreto como texto.

SHA-256
    → crea una huella determinística para almacenarlo.

PostgreSQL
    → recuerda la sesión.

Rotación
    → invalida el secreto anterior y entrega uno nuevo.
```

# Referencias conceptuales rápidas

```text
Token opaco
    = secreto aleatorio sin claims.

256 bits
    = 32 bytes de entropía.

CSPRNG
    = generador pseudoaleatorio apto para criptografía.

Base64URL
    = encoding binario → texto seguro para URLs/HTTP.

SHA-256
    = función hash criptográfica con salida de 256 bits.

Hash
    = huella irreversible y determinística.

Rotation
    = reemplazar cada refresh token después de utilizarlo.

Revocation
    = marcar una sesión como no válida.

Reuse Detection
    = detectar el uso de un token que ya había sido rotado.
```

# Resumen en una frase

> **Generá el refresh token con 256 bits aleatorios, entregá el valor real únicamente al cliente, almacená `SHA-256(token)` en la base de datos y reemplazá el token por uno nuevo cada vez que se utilice para renovar la sesión.**
