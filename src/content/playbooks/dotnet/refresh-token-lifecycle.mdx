# Contexto

> **¿Cuándo usar este playbook?**
>
> Cuando ya tenés autenticación mediante access tokens JWT y una capa de
> persistencia para refresh tokens, pero todavía necesitás construir el ciclo
> completo de sesión: emitir el refresh token, almacenarlo de forma segura en
> el navegador, utilizarlo para renovar el access token y rotarlo después de
> cada uso.

Este playbook continúa después de haber resuelto la persistencia.

La capa de persistencia ya debería permitir trabajar conceptualmente con:

```text
RefreshToken
├── TokenHash
├── UserId
├── ExpiresAt
├── RevokedAt
├── ReplacedByTokenHash
└── CreatedAt
```

y disponer de operaciones equivalentes a:

```text
FindByHashAsync
AddAsync
Revoke
SaveChangesAsync
```

Ahora vamos a construir encima de esa infraestructura:

```text
Login
  ↓
crear access token
  ↓
crear refresh token
  ↓
SHA-256
  ↓
guardar hash
  ↓
enviar token real como cookie HttpOnly
```

y posteriormente:

```text
POST /auth/refresh
       ↓
leer cookie
       ↓
SHA-256
       ↓
buscar hash
       ↓
validar
       ↓
revocar token anterior
       ↓
crear reemplazo
       ↓
guardar cambios juntos
       ↓
enviar nueva cookie
       ↓
devolver nuevo access token
```

---

# Objetivo arquitectónico

La separación de responsabilidades debería permanecer clara:

```text
Endpoint
   │
   │ HTTP
   │ cookies
   │ status codes
   ▼
AuthService
   │
   │ reglas de autenticación
   │ generación de tokens
   │ validación
   │ rotación
   ▼
IRefreshTokenRepository
   │
   │ persistencia
   ▼
RefreshTokenRepository
   │
   │ EF Core
   ▼
PostgreSQL
```

La regla central es:

> **El endpoint administra HTTP. El servicio administra autenticación. El
> repositorio administra persistencia.**

No introduzcas `HttpResponse`, `CookieOptions` o `HttpContext` dentro de
Application.

Tampoco introduzcas `AppDbContext` dentro de `AuthService`.

# Antes de empezar: access token y refresh token cumplen roles diferentes

## Access token

Normalmente:

```text
Access Token
├── JWT
├── corta duración
├── contiene claims
├── firmado
├── enviado mediante Authorization: Bearer
└── normalmente stateless
```

Por ejemplo:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

Puede durar:

```text
15 minutos
```

y contener:

```text
UserId
Email
Jti
Exp
Issuer
Audience
```

Su trabajo es:

```text
demostrar autorización durante poco tiempo
```

---

## Refresh token

Normalmente:

```text
Refresh Token
├── larga duración
├── secreto
├── opaco
├── aleatorio
├── no contiene claims útiles
├── representa una sesión renovable
└── requiere estado del servidor
```

Su trabajo es:

```text
conseguir nuevos access tokens
```

No debería utilizarse directamente para acceder a endpoints de negocio.

---

# ¿Por qué usar un refresh token opaco y no otro JWT?

Un refresh token también podría técnicamente ser un JWT.

Por ejemplo:

```text
Access token
JWT
15 minutos

Refresh token
JWT
7 días
```

Sin embargo, si necesitás:

```text
revocación;
logout;
rotación;
detección de expiración;
historial de sesión;
invalidación inmediata;
```

vas a necesitar estado en el servidor de todas formas.

Entonces el principal beneficio de un JWT:

```text
ser autocontenido y no consultar almacenamiento
```

prácticamente desaparece.

Un token opaco es más simple:

```text
random bytes
    ↓
Base64URL
    ↓
refresh token
```

No contiene:

```text
UserId
Email
Exp
Claims
Roles
```

El servidor obtiene toda la información desde su propia base de datos.

Una arquitectura habitual queda:

```text
Access Token
────────────
JWT
15 min
stateless


Refresh Token
─────────────
opaque random
7 días
stateful
hash persistido
```

# Paso 1: definir la configuración

No disperses números mágicos por el código.

Una configuración puede incluir:

```json
{
  "Jwt": {
    "Issuer": "my-api",
    "Audience": "my-frontend",
    "SecretKey": "...",
    "ExpiryMinutes": 15,
    "RefreshTokenLifetimeDays": 7,
    "RefreshTokenSizeInBytes": 32
  }
}
```

Y su options class:

```csharp
using System.ComponentModel.DataAnnotations;

namespace MyProject.Application.Identity.Options;

public sealed class JwtOptions
{
    public const string SectionName = "Jwt";

    [Required]
    public string Issuer { get; init; } = string.Empty;

    [Required]
    public string Audience { get; init; } = string.Empty;

    [Required]
    [MinLength(32)]
    public string SecretKey { get; init; } = string.Empty;

    [Range(1, int.MaxValue)]
    public int ExpiryMinutes { get; init; }

    [Range(1, int.MaxValue)]
    public int RefreshTokenLifetimeDays { get; init; }

    [Range(32, int.MaxValue)]
    public int RefreshTokenSizeInBytes { get; init; }
}
```

Después registrá:

```csharp
builder.Services
    .AddOptions<JwtOptions>()
    .Bind(
        builder.Configuration.GetRequiredSection(
            JwtOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

```text
RefreshTokenLifetimeDays = 0
```

al iniciar la aplicación y no cuando un usuario intente hacer login.

# Paso 2: generar un refresh token criptográficamente seguro

No uses:

```csharp
Random
```

No uses:

```csharp
DateTime.Now.Ticks
```

No uses:

```text
UserId + timestamp
```

No construyas secretos predecibles.

Utilizá:

```csharp
RandomNumberGenerator
```

de:

```csharp
System.Security.Cryptography
```

Ejemplo:

```csharp
private string GenerateRefreshToken()
{
    var bytes = RandomNumberGenerator.GetBytes(
        _jwtOptions.RefreshTokenSizeInBytes);

    return Convert
        .ToBase64String(bytes)
        .TrimEnd('=')
        .Replace('+', '-')
        .Replace('/', '_');
}
```

---

# ¿Por qué 32 bytes?

Un byte contiene:

```text
8 bits
```

Por lo tanto:

```text
32 bytes × 8 bits
= 256 bits
```

El secreto tiene:

```text
2^256
```

valores posibles.

Ese espacio de búsqueda es tan grande que intentar todos los valores mediante
fuerza bruta no es una estrategia práctica.

---

# ¿Qué hace Base64URL?

Después de generar los bytes:

```text
01101010
10100101
...
```

necesitamos transportarlos cómodamente como texto.

Base64 los convierte en caracteres.

Ejemplo conceptual:

```text
random bytes
    ↓
Base64
    ↓
dGVzdC8rPQ==
```

Pero Base64 tradicional puede contener:

```text
+
/
=
```

que pueden resultar incómodos en URLs, cookies o headers.

Por eso usamos una variante URL-safe:

```text
+  →  -
/  →  _
=  →  eliminado al final
```

Resultado:

```text
qW83koYRNdxOdfdoYsmWLDODLr8pTuv7WkUy6uvqpck
```

---

# Importante: Base64 NO es seguridad

Base64 es reversible.

Esto:

```text
bytes
  ↓
Base64
  ↓
string
```

también puede hacerse al revés.

Por eso:

> **Base64 es encoding, no encryption y no hashing.**

Recordá:

```text
Encoding
────────
Base64
reversible
no protege secretos


Encryption
──────────
AES
reversible usando una clave


Hashing
───────
SHA-256
no reversible
produce una huella
```

---

# Paso 3: entender SHA-256 antes de implementarlo

SHA significa:

```text
Secure Hash Algorithm
```

SHA-256 es una función hash criptográfica.

Conceptualmente:

```text
entrada arbitraria
       ↓
    SHA-256
       ↓
256 bits de salida
```

Por ejemplo:

```text
"hola"
   ↓
SHA-256
   ↓
un digest de 256 bits
```

La entrada puede tener:

```text
5 bytes
50 bytes
5 MB
```

pero el resultado de SHA-256 siempre tendrá:

```text
256 bits
```

---

# Hashing no es cifrado

Un algoritmo de cifrado tiene dos direcciones:

```text
plaintext
   ↓
encrypt(key)
   ↓
ciphertext
   ↓
decrypt(key)
   ↓
plaintext
```

SHA-256 no funciona así.

Existe:

```text
input
  ↓
SHA-256
  ↓
hash
```

pero no existe una operación:

```text
hash
  ↓
SHA256Decrypt()
  ↓
input
```

No hay una clave secreta que permita revertir el proceso.

---

# Entonces, ¿SHA-256 es imposible de romper?

La frase correcta no es:

```text
"es imposible descifrar SHA-256"
```

porque realmente **no hay nada que descifrar**.

Lo que un atacante puede intentar es:

```text
candidato 1
    ↓
SHA-256
    ↓
¿coincide con el hash?

candidato 2
    ↓
SHA-256
    ↓
¿coincide?

...
```

Eso se denomina buscar una **preimagen**.

Por ejemplo, si almacenás:

```text
SHA256("1234")
```

y alguien roba el hash, puede probar:

```text
SHA256("0000")
SHA256("0001")
SHA256("0002")
...
SHA256("9999")
```

Solamente existen:

```text
10.000
```

PINs de cuatro dígitos.

Aunque SHA-256 no sea reversible, el secreto puede adivinarse.

---

# El hash no es más fuerte que el secreto original

Esta regla es fundamental:

> **Hashing no agrega entropía al secreto.**

Si el secreto original es:

```text
password123
```

SHA-256 no convierte mágicamente esa contraseña débil en un secreto fuerte.

Un atacante puede calcular:

```text
SHA256("password")
SHA256("123456")
SHA256("password123")
...
```

muy rápidamente.

---

# ¿Por qué SHA-256 está bien para refresh tokens pero no para contraseñas?

Porque el refresh token:

```text
no lo escoge un humano
```

Lo genera:

```csharp
RandomNumberGenerator.GetBytes(32)
```

Entonces tiene aproximadamente:

```text
256 bits de entropía
```

No existe un diccionario útil de:

```text
password
admin
123456
qwerty
```

El atacante tendría que buscar dentro de un espacio aproximado de:

```text
2^256
```

posibilidades.

Por eso:

```text
random 256-bit refresh token
        +
SHA-256
```

es una combinación apropiada.

---

# En cambio, una contraseña necesita un algoritmo lento

Una contraseña suele tener poca entropía.

Por eso no deberías hacer:

```csharp
SHA256(password)
```

para almacenar passwords.

Para contraseñas se utilizan funciones deliberadamente costosas como:

```text
Argon2
BCrypt
scrypt
PBKDF2
```

Conceptualmente:

```text
PASSWORD
────────
humano
predecible
baja entropía

→ password hashing lento


REFRESH TOKEN
─────────────
máquina
aleatorio
alta entropía

→ SHA-256
```

---

# Paso 4: implementar SHA-256 para el refresh token

Podés crear:

```csharp
private static string HashRefreshToken(
    string refreshToken)
{
    var bytes =
        Encoding.UTF8.GetBytes(refreshToken);

    var hash =
        SHA256.HashData(bytes);

    return Convert.ToHexString(hash);
}
```

Necesitás:

```csharp
using System.Security.Cryptography;
using System.Text;
```

---

# ¿Qué ocurre exactamente aquí?

Primero:

```csharp
Encoding.UTF8.GetBytes(refreshToken)
```

transforma:

```text
"qW83ko..."
```

en bytes.

Después:

```csharp
SHA256.HashData(bytes)
```

produce:

```text
256 bits
```

Finalmente:

```csharp
Convert.ToHexString(hash)
```

representa esos bits como hexadecimal.

---

# ¿Por qué el resultado hexadecimal tiene 64 caracteres?

Cada carácter hexadecimal representa:

```text
4 bits
```

SHA-256 produce:

```text
256 bits
```

Entonces:

```text
256 / 4
= 64
```

Resultado:

```text
64 caracteres hexadecimales
```

Ejemplo conceptual:

```text
6F8DB599DE986FAB7A21625B7916589C...
```

Por eso una columna:

```text
varchar(64)
```

sería suficiente si siempre vas a utilizar SHA-256 hexadecimal.

Utilizar:

```text
varchar(128)
```

también es válido si querés dejar margen.

---

# Paso 5: entender cómo se valida sin descifrar

Supongamos que generamos:

```text
RT1 = qW83koYRNdxOdf...
```

Calculamos:

```text
HASH1 = SHA256(RT1)
```

En PostgreSQL almacenamos:

```text
HASH1
```

En el navegador:

```text
RT1
```

Cuando posteriormente llega:

```http
POST /api/auth/refresh
Cookie: refreshToken=RT1
```

hacemos otra vez:

```text
SHA256(RT1)
```

y obtenemos:

```text
HASH1
```

Entonces:

```sql
SELECT ...
FROM RefreshTokens
WHERE TokenHash = HASH1;
```

No hacemos:

```text
HASH1
 ↓
descifrar
 ↓
RT1
```

Hacemos:

```text
RT1 recibido
    ↓
SHA-256
    ↓
HASH1
    ↓
comparar
```

Este es el principio que debes recordar.

# Paso 10: modificar el login

Después de validar email y contraseña:

```csharp
var accessToken =
    GenerateJwtToken(user);
```

```csharp
var refreshTokenEntity = new RefreshToken

```

```csharp
await refreshTokenRepository.AddAsync(

    cancellationToken);

    cancellationToken);
```

Finalmente:

```csharp
return new LoginResult(
    LoginStatus.Success,
    new AuthResponse(
        accessToken,
        _jwtOptions.ExpiryMinutes * 60),
    new IssuedRefreshToken(
        refreshToken,
        refreshTokenExpiresAt));
```

# Paso 11: crear la cookie `HttpOnly`

La cookie debe crearse en API.

Por ejemplo:

```csharp
private const string RefreshTokenCookieName =
    "myapp.refreshToken";
```

Helper:

```csharp
private static void AppendRefreshTokenCookie(
    HttpResponse response,
    IssuedRefreshToken refreshToken,
    bool isDevelopment)
{
    var options = new CookieOptions
    {
        HttpOnly = true,
        Secure = !isDevelopment,
        SameSite = SameSiteMode.Lax,
        Expires = new DateTimeOffset(
            refreshToken.ExpiresAt),
        Path = "/api/auth"
    };

    response.Cookies.Append(
        RefreshTokenCookieName,
        refreshToken.Value,
        options);
}
```

---

# ¿Qué hace `HttpOnly`?

```csharp
HttpOnly = true
```

significa que JavaScript no puede leer la cookie mediante:

```javascript
document.cookie;
```

Eso reduce la exposición del refresh token ante determinados ataques XSS.

El navegador continúa enviando la cookie automáticamente cuando corresponde.

---

# ¿Qué hace `Secure`?

```csharp
Secure = true
```

indica:

```text
solo enviar cookie mediante HTTPS
```

En producción debería estar activado.

En desarrollo local puede necesitar una estrategia distinta dependiendo de si
utilizás HTTP o HTTPS.

---

# ¿Qué hace `SameSite`?

Controla cuándo se envía una cookie en solicitudes entre sitios.

Una configuración común:

```csharp
SameSite = SameSiteMode.Lax
```

puede funcionar cuando frontend y backend forman parte del mismo site.

Si la arquitectura es completamente cross-site, puede requerirse:

```csharp
SameSite = SameSiteMode.None
Secure = true
```

No copies `SameSite` ciegamente.

Debe analizarse según:

```text
dominio frontend
dominio backend
HTTPS
proxy
CORS
```

---

# ¿Por qué limitar `Path`?

```csharp
Path = "/api/auth"
```

hace que el navegador no envíe el refresh token a rutas que no lo necesitan.

Por ejemplo:

```text
/api/auth/login      ✓
/api/auth/refresh    ✓
/api/auth/logout     ✓

/api/accounts        no es necesario
/api/categories      no es necesario
/api/gym             no es necesario
```

Es una medida de minimización de exposición.

# Paso 12: completar el endpoint de login

Ejemplo con Minimal APIs:

```csharp
private static async Task<Results<
        Ok<AuthResponse>,
        UnauthorizedHttpResult>>
    LoginAsync(
        LoginRequest request,
        IAuthService authService,
        HttpResponse response,
        IWebHostEnvironment environment,
        CancellationToken cancellationToken)
{
    var result = await authService.LoginAsync(
        request,
        cancellationToken);

    if (result.Status ==
        LoginStatus.InvalidCredentials)
    {
        return TypedResults.Unauthorized();
    }

    if (result.Status != LoginStatus.Success)
    {
        throw new InvalidOperationException(
            $"Unknown login status: {result.Status}");
    }

    AppendRefreshTokenCookie(
        response,
        result.RefreshToken!,
        environment.IsDevelopment());

    return TypedResults.Ok(
        result.Auth!);
}
```

Responsabilidades:

```text
AuthService
───────────
validó
generó
persistió


Endpoint
────────
creó cookie
seleccionó HTTP 200/401
```

# Paso 13: preparar la consulta para el refresh

Para emitir un JWT nuevo normalmente necesitás información del usuario:

```text
UserId
Email
Claims
```

Si `RefreshToken` tiene:

```csharp
public User User { get; set; }
```

podés cargarlo:

```csharp
public Task<RefreshToken?> FindByHashAsync(
    string tokenHash,
    CancellationToken cancellationToken = default)
{
    return _dbContext.RefreshTokens
        .Include(refreshToken => refreshToken.User)
        .SingleOrDefaultAsync(
            refreshToken =>
                refreshToken.TokenHash == tokenHash,
            cancellationToken);
}
```

# ¿Por qué `Include(User)`?

Porque EF Core no carga automáticamente la navegación salvo que tengas
configurado lazy loading.

Entonces:

```csharp
storedRefreshToken.User
```

no debería asumirse disponible si la consulta no lo incluyó.

# ¿Por qué un solo `SaveChangesAsync`?

No hagas:

```csharp

```

Porque puede ocurrir:

```text

   ↓

   ↓

```

Resultado:

```text

```

La sesión queda destruida.

Queremos:

```text

├── RT1 Modified
└── RT2 Added
        ↓

        ↓
transacción
```

Si falla:

```text
rollback
```


# ¿Necesito `BeginTransactionAsync()`?

Para una única llamada a `SaveChangesAsync`, EF Core normalmente ya ejecuta
los cambios dentro de una transacción cuando el proveedor soporta
transacciones.

Por eso no es necesario introducir inmediatamente:

```csharp
_dbContext.Database.BeginTransactionAsync()
```

en `AuthService`.

Además eso acoplaría Application con EF Core.

La regla práctica:

```text
una operación lógica
+
un DbContext
+
un SaveChanges
```

suele ser suficiente para este caso básico.

Si en el futuro la operación cruza:

```text
varios SaveChanges;
varios DbContext;
servicios externos;
colas;
```

entonces el problema transaccional cambia.


Puede tratarse como una mejora posterior si no forma parte del alcance inicial.

# Paso 23: implementar `RefreshAsync` completo

Una implementación base:

```csharp
public async Task<RefreshResult> RefreshAsync(
    string refreshToken,
    CancellationToken cancellationToken = default)
{
    if (string.IsNullOrWhiteSpace(refreshToken))
    {
        return new RefreshResult(
            RefreshStatus.InvalidToken);
    }

    var tokenHash =
        HashRefreshToken(refreshToken);

    var storedToken =
        await refreshTokenRepository.FindByHashAsync(
            tokenHash,
            cancellationToken);

    var now = DateTime.UtcNow;

    if (storedToken is null ||
        storedToken.RevokedAt is not null ||
        storedToken.ExpiresAt <= now)
    {
        return new RefreshResult(
            RefreshStatus.InvalidToken);
    }

    var newAccessToken =
        GenerateJwtToken(storedToken.User);

    var newRefreshToken =
        GenerateRefreshToken();

    var newRefreshTokenHash =
        HashRefreshToken(newRefreshToken);

    var newRefreshTokenExpiresAt =
        now.AddDays(
            _jwtOptions.RefreshTokenLifetimeDays);

    var newRefreshTokenEntity =
        new RefreshToken
        {
            TokenHash = newRefreshTokenHash,
            UserId = storedToken.UserId,
            ExpiresAt = newRefreshTokenExpiresAt
        };

    refreshTokenRepository.Revoke(
        storedToken,
        now,
        newRefreshTokenHash);

    await refreshTokenRepository.AddAsync(
        newRefreshTokenEntity,
        cancellationToken);

    await refreshTokenRepository.SaveChangesAsync(
        cancellationToken);

    return new RefreshResult(
        RefreshStatus.Success,
        new AuthResponse(
            newAccessToken,
            _jwtOptions.ExpiryMinutes * 60),
        new IssuedRefreshToken(
            newRefreshToken,
            newRefreshTokenExpiresAt));
}
```

# Paso 25: implementar el handler `/refresh`

```csharp
private static async Task<Results<
        Ok<AuthResponse>,
        UnauthorizedHttpResult>>
    RefreshAsync(
        HttpRequest request,
        HttpResponse response,
        IAuthService authService,
        IWebHostEnvironment environment,
        CancellationToken cancellationToken)
{
    if (!request.Cookies.TryGetValue(
            RefreshTokenCookieName,
            out var refreshToken) ||
        string.IsNullOrWhiteSpace(refreshToken))
    {
        DeleteRefreshTokenCookie(response);

        return TypedResults.Unauthorized();
    }

    var result =
        await authService.RefreshAsync(
            refreshToken,
            cancellationToken);

    if (result.Status ==
        RefreshStatus.InvalidToken)
    {
        DeleteRefreshTokenCookie(response);

        return TypedResults.Unauthorized();
    }

    if (result.Status !=
        RefreshStatus.Success)
    {
        throw new InvalidOperationException(
            $"Unknown refresh status: {result.Status}");
    }

    AppendRefreshTokenCookie(
        response,
        result.RefreshToken!,
        environment.IsDevelopment());

    return TypedResults.Ok(
        result.Auth!);
}
```

# Errores comunes

| Error                                              | Por qué ocurre                                        | Solución                                               |
| -------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| Usar `Random`                                      | No es un CSPRNG                                       | Usar `RandomNumberGenerator`                           |
| Creer que Base64 protege el token                  | Base64 es encoding reversible                         | La seguridad viene de la aleatoriedad y SHA-256        |
| Guardar el token real                              | Una fuga de DB permite usar las sesiones directamente | Persistir solo `TokenHash`                             |
| Intentar descifrar SHA-256                         | Hashing no es encryption                              | Hashear nuevamente el token recibido y comparar        |
| Usar SHA-256 para passwords                        | Es demasiado rápido para secretos humanos             | Usar BCrypt, Argon2, scrypt o PBKDF2                   |
| Devolver refresh token en JSON                     | JavaScript puede acceder a él                         | Enviarlo mediante `HttpOnly` cookie                    |
| Guardarlo en `localStorage`                        | Mayor exposición ante XSS                             | Mantenerlo en cookie `HttpOnly`                        |
| Guardar dos veces durante rotación                 | Puede dejar una sesión inconsistente                  | Revocar + agregar + un solo `SaveChanges`              |
| Añadir `AppDbContext` a AuthService                | Rompe separación Application/Infrastructure           | Usar repositorios/contratos                            |
| Dar error diferente por token inexistente/revocado | Filtra información                                    | Responder 401 genérico                                 |
| Crear el reemplazo sin revocar el anterior         | Deja múltiples tokens válidos                         | Rotar siempre                                          |
| Reutilizar el mismo refresh token                  | No existe rotación real                               | Generar uno nuevo en cada refresh                      |
| Usar `AddMinutes(RefreshTokenLifetimeDays)`        | Error de unidad temporal                              | Usar `AddDays(...)`                                    |
| Olvidar cargar `User`                              | No se puede regenerar JWT                             | Usar `Include` o consulta específica                   |
| Borrar cookie con otro `Path`                      | El navegador puede conservarla                        | Usar el mismo Path                                     |
| Pensar que un `SaveChanges` soluciona concurrencia | Atomicidad y concurrencia son problemas diferentes    | Añadir estrategia específica si el alcance lo requiere |

# Sobre SHA-256: propiedades que conviene recordar

## Determinismo

Misma entrada:

```text
SHA256(X)
```

siempre produce:

```text
mismo hash
```

---

## Avalanche effect

Un cambio mínimo:

```text
"ceres"
"Ceres"
```

produce hashes completamente diferentes.

---

## Resistencia a preimagen

Dado:

```text
HASH
```

debería ser computacionalmente impracticable encontrar:

```text
INPUT
```

tal que:

```text
SHA256(INPUT) = HASH
```

---

## Resistencia a segunda preimagen

Dado un mensaje:

```text
M1
```

debería ser impracticable encontrar:

```text
M2 != M1
```

que produzca el mismo hash.

---

## Resistencia a colisiones

Debería ser impracticable encontrar dos mensajes arbitrarios:

```text
M1 != M2
```

tales que:

```text
SHA256(M1) = SHA256(M2)
```

---

# ¿Por qué pueden existir colisiones matemáticamente?

SHA-256 acepta entradas prácticamente arbitrarias:

```text
cantidad gigantesca de inputs
```

pero solamente dispone de:

```text
2^256
```

outputs posibles.

Por el principio del palomar necesariamente existen entradas distintas con el
mismo hash.

Lo importante criptográficamente es que encontrarlas sea impracticable.

---

# Diferencia entre hash, salt y pepper

Para refresh tokens aleatorios de alta entropía normalmente no necesitás
agregar un salt para defenderte de ataques de diccionario como ocurre con
passwords.

¿Por qué?

Porque cada token ya es esencialmente:

```text
256 bits aleatorios
```

Dos tokens generados correctamente prácticamente nunca serán iguales.

En cambio, passwords humanos pueden repetirse:

```text
password123
password123
password123
```

y por eso requieren mecanismos diseñados específicamente para password
hashing.

No copies automáticamente el esquema de password hashing al almacenamiento de
refresh tokens.

# Checklist final

## Generación

- [ ] El refresh token usa `RandomNumberGenerator`
- [ ] Se generan al menos 32 bytes aleatorios
- [ ] El token se representa mediante Base64URL u otra codificación segura para transporte
- [ ] No se utilizan timestamps, `Random`, IDs de usuario ni valores predecibles

## SHA-256

- [ ] El refresh token real se convierte a bytes
- [ ] Se calcula SHA-256
- [ ] PostgreSQL guarda solamente el hash
- [ ] Se entiende que SHA-256 no se descifra
- [ ] La validación consiste en volver a hashear y comparar
- [ ] No se utiliza SHA-256 como reemplazo de un password hasher

## Login

- [ ] El login sigue validando credenciales
- [ ] Se genera un access token
- [ ] Se genera un refresh token
- [ ] Se persiste exclusivamente su hash
- [ ] La expiración del refresh token utiliza días correctamente
- [ ] La respuesta JSON no contiene el refresh token
- [ ] El refresh token se envía como `HttpOnly` cookie

## Cookie

- [ ] `HttpOnly = true`
- [ ] `Secure = true` en producción
- [ ] `SameSite` fue decidido conscientemente
- [ ] `Path` limita dónde se envía la cookie
- [ ] El token no se almacena en `localStorage`
- [ ] El token no se almacena en `sessionStorage`
- [ ] El token no se coloca en React Context

## Refresh

- [ ] Existe `POST /auth/refresh`
- [ ] El endpoint no recibe el refresh token en JSON
- [ ] Lee el token desde la cookie
- [ ] El servicio calcula SHA-256
- [ ] Busca por `TokenHash`
- [ ] Comprueba existencia
- [ ] Comprueba expiración
- [ ] Comprueba revocación

## Atomicidad

- [ ] Revocación y creación utilizan el mismo `DbContext`
- [ ] Se preparan ambos cambios antes de persistir
- [ ] Se ejecuta un único `SaveChangesAsync`
- [ ] Application no depende directamente de `AppDbContext`

## Errores

- [ ] Cookie ausente → 401
- [ ] Token desconocido → 401
- [ ] Token expirado → 401
- [ ] Token revocado → 401
- [ ] La cookie se elimina cuando el refresh es inválido
- [ ] La respuesta no explica cuál condición exacta falló

# Modelo mental para recordar SHA-256

Si dentro de seis meses olvidás cómo funciona, recordá:

```text
TOKEN REAL
    │
    │ SHA-256
    ▼
HASH
```

No existe:

```text
HASH
    │
    │ decrypt
    ▼
TOKEN REAL
```

Para validar:

```text
token recibido
      │
      ▼
   SHA-256
      │
      ▼
hash calculado
      │
      ▼
¿igual al hash guardado?
      │
   sí / no
```

Y la seguridad depende de que el token original sea:

```text
aleatorio
impredecible
alta entropía
```

Por eso:

```text
RandomNumberGenerator
        +
256 bits
        +
SHA-256
```

funciona bien para refresh tokens.

# Qué implementar después

Una vez terminado este playbook, los siguientes bloques naturales son:

1. **Refresh automático en el frontend**

   - interceptor de responses;
   - detectar 401;
   - llamar `/refresh`;
   - actualizar access token;
   - reintentar request;
   - evitar múltiples refresh simultáneos;
   - evitar loops infinitos.

2. **Logout backend**

   - leer refresh cookie;
   - hashear;
   - encontrar sesión;
   - revocarla;
   - eliminar cookie;
   - responder `204 No Content`;
   - mantener comportamiento idempotente.

3. **Protección de rutas**

   - distinguir sesión inicializando;
   - sesión autenticada;
   - sesión no autenticada;
   - intentar restaurar sesión mediante `/refresh` al arrancar.
